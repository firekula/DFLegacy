# 无历史上下文的 agent 工作步骤

适用：任何模型或 agent 工具接手开发、诊断、文档和运维。入口：[START-HERE](../../START-HERE.md)；文件定位：[模块地图](repository-map.md)；实际命令：[构建测试发布](build-test-release.md)。本流程不依赖 Codex、Claude、Gemini、技能插件或特定记忆服务。

## 1. 把任务限制到可验证的范围

开始前写四句话：用户看到的症状/需要的行为；第一章、第二章或共用；准备修改的模块；怎样证明完成。例如：“第二章登录页显示正在运行程序集的发行号；修改 Launcher 的版本显示；检查程序集版本与窗口文字，不把 Git hash 拼到版本标签。”

“修复所有网络问题”“完全还原全部玩法”无法作为一个实现步骤。拆为一次连接、一个协议、一个状态转换或一个界面行为。一次只保留一个主要假设，其他发现记入后续项。

## 2. 先确认工作区

```powershell
git status --short
git branch --show-current
git rev-parse HEAD
git diff --stat
```

已有改动视为用户或并行工作的内容。记录它们，避免覆盖。不自行执行 `git reset --hard`、`git clean -fdx` 或大范围还原。仅在任务需要隔离时创建工作区；不要把现有客户端运行目录当源码输出目录。

检查工具链版本时读 [global.json](../../global.json)、对应 `.csproj`、`.vcxproj`、`CMakeLists.txt` 和构建脚本。不要靠旧聊天中的版本安装依赖。

## 3. 少量、精确地读代码

1. 先读一页专题手册和入口文件。
2. 搜符号，再读调用方、实现、测试这三处。
3. 找到修改点后停止无关全文检索。大型 `Program.cs`、`GameProtocolEngine` 的 partial 文件按功能定位。

```powershell
rg --files src tests tools protocol deploy
rg -n 'TryAdvanceRoom|Cemetery' src/DFLegacy.Server tests/DFLegacy.SmokeTests
rg -n 'LauncherVersion|InformationalVersion' src/DFLegacy.Launcher src/DFLegacy.Startup
git log -5 --oneline -- src/DFLegacy.Server/DungeonInstance.cs
```

PowerShell 下不要把 `src/*Endpoints.cs` 当作一定会被 shell 展开的路径；使用 `rg -g '*Endpoints.cs' pattern src`。若没有 `rg`，用 `Get-ChildItem` 和 `Select-String`。文件不存在先查文件名，不能凭惯例新建一个同名替代实现。

## 4. 区分事实与假设

| 观察 | 允许的结论 | 不能推出 |
| --- | --- | --- |
| 静态代码里有 handler | 有实现路径 | 真机正确调用、协议字段正确 |
| 测试通过 | 本次命令覆盖的断言通过 | 全部功能完成 |
| 日志发出了放行通知 | 服务端执行了发送 | 客户端门碰撞和换房一定正常 |
| 更新包构建成功 | 制包完成 | 每个更新源可下载、用户迁移成功 |
| 外部依赖文件找不到 | 当前环境缺文件 | 功能不存在、该检查可以删除 |

先记录失败现象和最短复现，确认错误发生层：资源 → 客户端读取 → 发包 → 服务端解析 → 状态变更 → 持久化 → 回包 → 客户端应用。不要用修改后面的状态掩盖前面的错误。

## 5. 实施与并行

- 在现有模块增加最小必要改动；避免顺便重命名、批量格式化或重构无关模块。
- 修改协议时一并检查发送端、接收端、章别、长度、编码、回包与失败分支。
- 修改存档/经济时检查重复请求、保存失败、重启、断线和跨会话缓存。
- 修改原生代码先确认二进制版本和地址特征；不能用“进程没崩”替代行为验证。
- 并行 agent 需要明确文件归属和交付条件。同一文件由一个 agent 写，其他只评审；记录每份结果对应的提交/产物。
- 不具备多 agent 能力时按同样子任务顺序执行即可。

## 6. 验证与恢复

按 [测试手册](testing-and-evidence.md)选择最低充分验证，再补受影响集成链路。界面实际检查标题、长文本、按钮、关闭、Tab/Enter/Esc 焦点和常用缩放。协议/原生改动记录参与人数、角色、房间、章别和实际加载的 DLL 哈希。

测试前后记下配置/存档摘要、占用端口、自己启动的进程和临时文件。测试使用克隆存档；停止自己启动的测试进程并恢复临时配置，不误停他人的服务。需要生产变更时按用户已给授权执行；缺少明确授权的真实发布、数据迁移或外部发送，应先准备具体方案和可审查产物再确认。

记录命令、退出码和日志路径。工具缺失、超时、跳过、测试失败分别报告。不要把没有执行的命令写成通过，也不要删除检查让结果变绿。

## 7. 小上下文接续

上下文接近耗尽时，将以下内容写入一个任务记录（无敏感数据），并让下一轮先读它：

```text
目标、范围和禁止变更项：
源码 HEAD、已存在改动、我的改动：
已经确认的事实（路径:符号或日志）：
已排除的假设及原因：
正在验证的唯一假设：
最后执行命令、退出码、输出位置：
仍运行的进程/占用端口/临时配置：
下一条命令和成功判据：
```

长期事实进入专题手册，单次事故进入 `knowledge/decisions/YYYY-MM-DD-主题.md`。避免依赖未跟踪的临时目录作为唯一证据。

## 8. 完成判据

- 用户要求的行为已实现，或已把真实阻断和可继续部分明确分开。
- 验证与改动匹配，涉及运行产物时身份可核对。
- `git diff --check` 无新增空白错误，差异不含账号、口令、令牌、私钥或用户存档。
- 对应配置、操作、测试和限制文档同步；不把本次完成说成旧遗留项全部完成。
- 最终交接包含修改点、验证结果、未覆盖范围、产物/文档路径和下一步。
