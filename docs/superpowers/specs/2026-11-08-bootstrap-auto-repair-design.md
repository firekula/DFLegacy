# Fixed startup entry and automatic repair

User approved implementation of the three-part proposal, both x86 and x64, with Gitea-only tests covering deleted/corrupt launcher and interrupted updates. This document records that approved scope; it does not request a second approval. Do not touch production, formal GitHub updates, Chapter 2, or `G:/dnf_local/DNF_2008`.

## Approach

Keep the existing shortcut target `DFLegacy.Launcher.exe` as a small native Windows entry. Move the full managed UI to `DFLegacy.Launcher.App.exe`; ship a separate `DFLegacy.Updater.exe` using the existing managed runtime and V4 repair engine. The updater runs briefly during startup verification/update and exits after opening the UI; no service or resident background updater. The native entry has no dependency on the UI executable or its managed runtime. A manual repair EXE alone was rejected because users would still have to find and invoke it. Keeping the temporary helper alone cannot recover a deleted launcher.

Builder choices: native C++/Win32 with static runtime and BCrypt SHA256, existing .NET 10 WPF binary reused for updater and UI roles. x86/x64 are separate entry/updater/UI variants; game patch remains x86. This is a Windows 10/11 test build, not new Windows 7 support. Native entry keeps the same path and icon; no change to existing shortcuts.

## File and process contract

- Root files: `DFLegacy.Launcher.exe` (native), `DFLegacy.Launcher.App.exe` (managed UI), `DFLegacy.Updater.exe` (managed updater), `DFLegacy.Bootstrap.ini`, existing client DLL and selected resources. Root UI/updater may have identical bytes in this implementation; V4 content-addressing deduplicates transport.
- Descriptor is ASCII/UTF-8 without BOM, CRLF or LF, exact `[Bootstrap]` section with `SchemaVersion=1`, `Architecture=x86|x64`, `LauncherSha256=<64 lowercase hex>`, `UpdaterSha256=<64 lowercase hex>`. No paths or URLs in descriptor. Fixed executable names only. Bounded length 4096; reject duplicate/unknown sections/keys and unsupported schema/architecture.
- Protected recovery state: `.dflegacy/bootstrap/recovery.ini` uses the same descriptor format; the only recovery executable is `.dflegacy/bootstrap/<UpdaterSha256>.exe`. Never treat unvalidated bytes as an updater. Recovery records are local receipts, not a defense against an attacker replacing every local trust record.
- Native entry selects validated primary updater or validated recovery executable, copies it into a unique native-owned temporary directory, verifies the copy, starts it with `--bootstrap-client <absolute client root> -- <original arguments>`, waits, and cleans its own temporary copy after exit. No arguments/passwords in logs. Success exit 0, cancel 2, failure 1. On primary failure 1 (not cancellation), it may try a different valid recovery hash once; no loops. Original arguments use correct Windows quoting.
- A validated primary is cached by hash before launch, but `recovery.ini` advances atomically only after updater exit 0. A failed new updater preserves the previous recovery selection. First starter seeds baseline recovery. The current primary can be replaced while the temporary updater runs; an older known-good recovery remains usable until the new updater itself completes a subsequent start.
- Entry rejects reparse traversal, malformed descriptors, incompatible architecture, unexpected cache names and unsafe temp paths; hash-check held read handles where practical. A per-installation `.dflegacy/bootstrap/entry.lock` serializes bootstrap work. `.dflegacy/bootstrap/app.lock` held by the UI prevents duplicate launches. Cancel/failure never starts game/UI without validation.
- Updater operates outside the client root and reuses `RepairClient`/`UpdateEngine`/`InstallTransaction`. It restores an interrupted transaction first, then checks the configured source, repairs only mismatches, verifies all files and migrations, and launches `DFLegacy.Launcher.App.exe --bootstrap-verified -- <original arguments>` with root working directory. It must reject manifests lacking the fixed bootstrap layout before applying them, preserving the last entry against accidental legacy-source downgrade. Offline launch only follows the existing fully verified installation rule, with an explicit notice.
- Updater progress uses existing updater window and confirmation for occupied processes; no silent termination. After success it closes. Updater GUI is independent of external client assets and damaged launcher config is preserved, not replaced with blank accounts.
- UI with bootstrap layout requires a validated installed receipt and descriptor and keeps the app lock. Directly opening the UI without the internal flag redirects to the fixed entry. A validated bootstrap UI does not run a duplicate automatic update check; its manual check routes through the fixed entry. Existing monolithic startup/helper paths remain unchanged for old packages.

## Publishing and migration

Use Gitea provider `gitea`, channel `gitea-test`, origin `http://firekula.site:3000`, repository `firekula/DFLegacy`. Immutable tags `v0.1.8-giteatest.3` / `.4`, sequences 3 / 4. Keep .1/.2. Four variants x86/x64 × normal/test. Existing V4 .2 can migrate using its existing helper: replace the entry, add UI/updater/descriptor, then restart the unchanged entry path. Include existing managed probes/DLLs to preserve managed-history completeness. Native entry remains byte-identical between .3 and .4; .4 changes managed engine version and test resource to exercise updater self replacement.

New bootstrap starters use a V4 installed receipt from an already built compatible manifest, fixed entry/UI/updater/descriptor, preserved user config, and seeded recovery engine. Do not broaden old schema-2/V3 archive allowlists to pretend bootstrap is an old package. Preserve source settings through an explicit opt-in script / existing Gitea test configuration. Packaging verifies each PE architecture, descriptor hashes, manifest hashes, exact resource allowlist and excluded private paths. No uploads of configuration/recovery caches from user directories; recovery files in a starter are generated solely from the built public updater.

## Acceptance

Native unit/process tests: malformed descriptor, duplicate keys, wrong architecture/hash, Unicode/spaces, denied links, primary missing/corrupt, recovery fallback, cancellation, bounded retry, exclusive lock, atomic recovery-record advancement. Managed tests: old-launcher behavior preserved, manifest-layout guard before writes, offline complete vs corrupt, config preservation, recovery validation, UI handoff only after full validation.

Actual x86/x64 binaries, isolated copies only: ordinary bootstrap; delete UI; corrupt same-length UI; delete/corrupt primary updater with known-good backup; interrupt a genuine V4 install after a commit checkpoint and terminate its worker, then launch the same original shortcut and observe recovery + valid UI. Test interruption while upgrading .3 to .4, retaining known-good updater. Use a harness with synchronous progress callback to pause production `InstallTransaction.Apply`; no production sleep/test backdoor. Verify fresh original-shortcut target identity, real Gitea manifest/download evidence, final all-file hashes, preserved settings, no pending journal and visible login window. No game login/online-account mutation needed. Independently verify original client hashes unchanged.

## Limits

Deleting the native entry and all recovery components still requires restoring the starter. OS socket reservations, disabled networking, denied writes, disk failures, missing recovery evidence or corruption of all copies cannot be silently fixed. The updater reports a clear failure and keeps evidence. This feature does not solve the prior Windows TCP 2311 reservation.
