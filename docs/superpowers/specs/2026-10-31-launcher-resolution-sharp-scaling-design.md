# 登录器分辨率设置与清晰平滑缩放

日期：2026-10-31。状态：用户已选择静态对比中的“清晰平滑”，并明确批准按设计实施、测试和发布。基线 `aba40c4`，隔离的现有工作树分支 `codex/launcher-resolution-scaling`。设计提交为 `bc8cf99`，本文件随后更新批准状态和实测编码边界。

## 目标与已经确定的取舍

用户希望直接在登录器选择游戏分辨率，并改善 800×600 窗口中的显示。用户先要求效果对比，随后明确选择“清晰平滑”。所选算法是先将 640×480 画面用最近邻整数放大，再双线性缩到目标尺寸。它改善非整数缩放的观感，不声称 800×600 是严格像素完美，也不会生成原素材没有的细节。

原型位于本聊天的 `dnf-scaling-comparison.html`；私有证据 `D:/DFLegacyCI/validation/scaling-preview-20261031`。输入是用户已有同版本客户端保存的原生 640×480 JPG，未从 800×600 截图反推；原型验证了静态算法、整数像素块与交互，不代表 D3D8 实机或性能已经通过。

构建者建议保留现有 D3D8 和 ijl15.dll，在整帧输出处实现缩放。后端选择是本设计的推荐，用户目前确定的是视觉效果。正式实现需以真实客户端和 GPU 验收为准。

## 方案比较

| 方案 | 取舍与决定 |
| --- | --- |
| 只改现有纹理采样 | 改动小，但当前代码只钩住 SetTextureStageState，无法控制最后将640×480呈现到窗口的缩放；不能交付已选算法，不采用 |
| D3D8 最终输出增加 GPU 缩放 | 保留原游戏绘制及格式，输出统一可控；需要处理状态还原、资源生命周期和设备重置。推荐，作为本设计的实现路线 |
| D3D8 转译为 D3D9/新后端再加着色器 | 可扩展更多滤镜，但增加第三方运行层及兼容范围；所选效果不要求它，本轮不引入 |

不增加游戏视野，不修改地图/UI布局或字体素材，不改为宽屏，不加入xBRZ/AI重建，也不改服务端或NPKStudio。保持原有单文件登录器分发方式，新增实现编入已有DLL，不增加图形代理DLL或额外运行时。

## 登录器中的使用方式

1. 保留当前“设置”入口，将连接配置和“游戏显示”分成页签。显示页明确标出实际客户端路径。
2. 显示页提供640×480、800×600、960×720、1024×768、1280×960、1600×1200预设；均为4:3。640为原尺寸，1280为精确2倍，800保留用户希望使用的大小。不提供自由拉伸和实时拖动改大小。
3. 画质提供“清晰平滑（推荐）”“清晰”“平滑”“旧版兼容”。清晰平滑采用本次选定算法；清晰/平滑也只处理最终整帧。旧版兼容保留现有纹理采样及原呈现链路。
4. “保存显示设置”独立写入显示配置，连接页仍保存原launcher.json。避免一次保存跨两个配置文件而出现部分成功。切换页签本身不写盘，取消不写盘。
5. 客户端路径以已保存的连接配置为准；连接页改了路径但尚未保存时，显示页禁止写入并提示先保存路径。路径不存在、配置不可读或保存失败须明确提示，不把失败显示为成功。
6. 保存后提示“下次启动游戏生效”，不重启/终止正在运行的游戏。超过当前显示器工作区的预设可提示但不自动更改用户选择；画面尺寸指游戏客户区的物理像素，窗口边框另计。
7. 现有尺寸不在预设中时显示“当前自定义尺寸”，打开页面不强行修改。只有用户选择受支持的4:3预设才能保存新的增强模式。未保存的旧尺寸仍由旧行为处理。

以上预设、页签与独立保存是构建者决定，不是用户原话；没有必要再让用户决定字段名和内部结构。

## 配置契约与兼容

以DNF.exe旁的Config.ini作为显示配置唯一来源，不在launcher.json再保存另一份分辨率。管理键：

```ini
[Resolution]
Width=800
Height=600

[Rendering]
PresentationFilter=sharp
```

PresentationFilter取值为sharp、point、linear、legacy；不复用旧ScaleFilter的语义。ScaleFilter保留给legacy，新输出模式保留游戏提交的原始纹理采样，不再将全部素材强制改成某个滤镜。

- 新建的默认INI采用800×600与sharp。旧INI没有PresentationFilter时继续legacy；未知/不支持的值进入legacy并记录原因，不损坏原配置。
- 本机最终部署时先备份，再按用户本次选定的效果将PresentationFilter保存为sharp；宽高保留已有支持值或用户在显示页的新选择。其他用户已有INI不因升级被整份覆盖。
- 写入只更新这三个管理键；保留其他节、注释、编码/BOM和换行。重复节/键须与原生读取行为一致地规范管理键，防止“已保存但旧值仍生效”。
- 写入前读取快照，暂存、原子替换；文件被锁定或期间外部编辑时拒绝覆盖并提示重载。失败保留旧文件。仅在字节实际变化时替换，避免无意义重写。
- 显示页不修改Network、账号、调试选项及其他玩家配置；原先安装器更新账号服务URL的行为独立保留，并与显示编辑使用同一套保持字节的INI基础能力。
- Config.ini缺失时从内嵌默认值创建；已有损坏/不支持编码应报错，不能用默认文件覆盖。支持原生读取器可识别的ANSI、UTF-8与UTF-16LE；UTF-32、UTF-16BE和UTF-8 BOM导致首行节被原生API忽略的文件拒绝显示编辑，避免声称保存成功但游戏读不到。Windows原生读取实测确认这些边界。

## D3D8呈现链路

当前window_scaling保留内部640×480参数，仅修改外部窗口尺寸。当前d3d8_scaler通过Direct3DCreate8 IAT和CreateDevice获取设备，只重写纹理过滤。新模式应接管Present边界，不在游戏精灵逐个绘制时重采样。

正常窗口模式的数据流：

```text
原游戏及其叠加层绘制640×480原始backbuffer
  → GPU复制到可采样源纹理
  → 最近邻放大k倍至中间渲染目标
  → 双线性缩到与游戏客户区同尺寸的独立呈现swap chain
  → 直接Present，避免运行库再拉伸一次
```

- `k=ceil(max(W/640,H/480))`。800×600时k=2，中间有效尺寸1280×960；1600×1200时k=3。640原尺寸及精确整数倍走像素等价的短路径，无额外柔化。
- point直接从原帧最近邻到目标；linear直接双线性；legacy调用原路径。增强模式只接受支持的4:3窗口客户区，内部坐标及原截图来源仍为640×480，不加入黑边或改变游戏视野。
- 实机补充：800旧版和增强模式的对照确认，原有窗口放大已经导致鼠标指针/命中测试偏移。增强模式在DispatchMessage边界将窗口客户区鼠标坐标换算到原640×480坐标；滚轮的屏幕坐标保留，仅在原滚轮命中测试转为客户区后换算。拖动按钮状态与负坐标保留；直接调用原生输入函数的合成输入不重复换算。legacy沿用原行为。此项是实测后记录的实现修正，见执行账本与验收报告。
- 采用同一设备的额外窗口swap chain作为输出，保留主设备/主backbuffer的原尺寸与游戏对其的观察。目标backbuffer与实际客户区逐像素匹配。原游戏若使用不支持的Present参数或非窗口模式，按下述失败规则处理，不能擅自改为系统全屏。
- 生产路径不进行每帧CPU读回，不依赖D3D编译器；固定功能GPU纹理绘制即可。源纹理/中间纹理/输出链按设备和尺寸缓存。
- 对齐D3D8屏幕像素中心与有效纹理坐标；禁止二次系统拉伸、边缘读到填充区、wrap采样和颜色/alpha混合污染。若设备要求POT纹理，分开记录分配尺寸与有效尺寸并正确处理边界；能力或资源上限不满足时执行明确降级，不能越界申请。
- 增强输出前核对客户区逻辑尺寸与物理尺寸；检测到系统DPI虚拟化的额外拉伸时，以dpi-virtualized明确回退，不自动修改系统/兼容性设置。本机正常比例与真实GPU路径验收；其他DPI设置不通过修改用户桌面来测试。
- 原绘制状态完整恢复，包括render target、深度、viewport、纹理/采样、shader/FVF、流/索引和相关渲染状态。Present返回后下一帧应与未增加后处理时保持相同的游戏状态。不得把DrawPrimitiveUP等调用对流绑定的副作用留给客户端。
- Hook和资源状态按设备管理，禁止共用一个全局Original函数指针假定所有设备相同。重入保护避免后处理触发自身或合成输入重复泵。
- Reset前释放持有的默认池资源和输出链；成功Reset后按新客户区惰性重建。设备丢失期间保留正确HRESULT，不拿上一帧伪装成功；最小化不分配0尺寸目标；恢复后重新输出。
- Release/QueryInterface/AddRef与资源引用关系必须保证没有设备自引用循环、悬空vtable或旧上下文复用。具体COM包裹/钩子管理方法留给构建者，但必须通过多次创建设备/销毁、Reset失败/重试及资源计数测试，不能用“进程退出会清理”代替正确释放。
- 格式以实际设备/表面能力为准。构建者可选合适的同格式中间资源；只允许经过验证的转换，不偷偷改变游戏色彩空间。现有图像输出、合成输入、FPS叠加和网络功能必须回归。

## 失败与可观察性

窗口尺寸/图形能力不支持、分配或复制/绘制失败时，原主backbuffer尚完整，回到原Present使游戏继续可用。该帧标记为“原呈现回退”，不宣称与显式legacy的旧纹理策略逐像素相同；不能事后重画整帧来伪装已应用旧策略。输出状态恢复失败则不能假装后处理成功；保留/报告底层错误并清理本设备的增强资源，避免带坏状态继续画。设备丢失必须传播并参与原游戏恢复逻辑，不能被兼容降级吞掉。

启动及有效模式变更写一次简短诊断到独立的客户端本地渲染日志：请求模式、实际模式、逻辑/输出/中间尺寸、格式与能力、降级原因/HRESULT。失败去重限频，不每帧刷盘，不记录账号或启动密文。显示页区分请求设置与最近一次实际运行结果；降级不能显示成“清晰平滑已经生效”。旧运行记录须标识时间/PID，不当作当前进程状态。

## 验收与发布门槛

1. 先为配置行为建立失败回归：不同编码/换行/重复节、现有自定义项、取消不写、路径切换、锁定、竞争和失败保留原字节。覆盖保存后原生读取的实际值，不只测字符串。
2. 缩放数学参考与预览一致：640原尺寸、800的两步采样、960/1024非整数尺寸、1280严格2×2像素块；检查纹理边缘及POT填充不渗色。RGB格式转换后的容差必须明确，整数可精确路径不允许任意容差掩盖错误。
3. 使用真正D3D8设备运行生产后处理代码的独立GPU测试，读回仅用于测试；比较输出、前后状态以及主backbuffer不变。伪COM测试负责失败与生命周期，不代替GPU和游戏验收。
4. 真实客户端自测800×600清晰平滑、640与1280，核对文字/人物/透明效果、点击/悬停、截图、最小化还原、Alt+Tab及设备恢复。确认输出尺寸、实际启用模式和诊断。测试账号与输出在私有证据目录，原资源不改。
5. 同机同画面预热后比较legacy与sharp的帧间隔和资源占用，记录中位/p95及尖峰与测量方法，区分CPU计时与GPU计时。800模式新增呈现段CPU耗时p95以不高于1ms为初始目标；若未达，先分析优化或与用户说明取舍，不据静态预览宣称无性能影响。
6. 新增图形GPU测试在可用Windows桌面上实际运行；CI没有图形会话时明确列出该项未执行，不能把跳过称为GPU通过。现有Launcher、原生、两端托管、发行工具与Docker门禁保持；原705测试+592子用例的保护不削弱。
7. 独立整支复核后提交推送main，Gitea完整构建/发布成功，再认证下载核对客户端包内的新DLL/登录器、清单及摘要。保持两个单文件服务程序及单文件玩家登录器形式；macOS/Linux服务包不增加Windows图形依赖。
8. 实际客户端安装前备份EXE、DLL和配置摘要，只有确认通过的新程序与用户选定显示键进入本机目录；游戏资源/存档保持。保护main既有3个未提交跟踪文件和163条状态记录，以及用户正在运行的服务。测试时临时启用Runner，完成后恢复原暂停状态。

## 构建者可直接决定的细节
