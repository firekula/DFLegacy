# 客户端逐文件更新、自修复与独立故障报告

日期：2026-11-08。状态：用户已批准实现及自动测试，Gitee 测试发布已授权；正式 GitHub 与线上版本不变。

## 1. 目标与已确定的选择

用户要求：崩溃、掉线、错误分别产生容易定位的报告；更新覆盖 NPK、PVF、DLL、EXE 等受管理文件；每次启动检查实际文件，成功或失败后的下一次启动也必须检查；只重新下载变化、缺失或损坏的文件；配置支持保留玩家数据的增量迁移；离线打包工具继续负责生成和上传 GitHub，保留 x86 / x64 两条更新线。

用户已选择：

- 本期采用逐文件差量下载和断点续传，不实现文件内部二进制差分。
- 无法连接 GitHub 时，若本地通过最近一次可信清单的完整校验，允许启动，明确提示“未确认线上最新版本”。
- 用户指定 `https://gitee.com/firekula/DFLegacy.git` 作为新热更测试仓库，可在此发布用于验收的资源。既有 GitHub 正式更新源不因此自动切换。

“热更”在本设计中指登录器自动更新：可以提前下载；安装会等游戏释放文件，不在正在运行的游戏中覆盖 DLL/PVF/NPK。

实现仅在第一章现有隔离工作区进行，不修改第二章工作区，不部署线上、不发奖励。Gitee 测试发布已获授权，正式 GitHub/线上发布另按用户发布要求执行。

## 2. 当前代码的限制与保留能力

- `ClientPackageManifest.Parse` 的 schema 2 只接受登录器、客户端 DLL、可选 PVF 和测试版 debug.dll；不支持普通资源目录。
- `UpdateSession.CheckAsync` 先调用 `LoadAndValidate`，旧安装损坏会在获取线上修复目标前失败。
- `GitHubUpdateClient.CheckAsync` 依赖 Release ID/版本过滤，不能作为同版本文件健康检查的依据；检查超时当前为 5 秒。
- `UpdateDownload.FetchAsync` 下载完整 ZIP，失败后删除暂存目录。没有逐文件缓存/Range 恢复；ZIP 和解压上限为 256/512 MiB。
- 已有 SHA256、更新助手、互斥锁、备份、持久事务记录、恢复和安装后校验。应复用、扩展并测试，不用简单覆盖复制替代。
- 更新异常常直接显示 `ex.Message`，启动失败有些路径只记异常类型；中继错误混在 launcher.log。普通版缺少可直接追踪原生故障地址的报告。
- 当前配置是 `launcher.json`，不是 launcher.txt；账号、服务器、用户设置和中继配置共存，不能按线上整个文件的哈希强行覆盖。

## 3. 方案比较与研究依据

### 已选：V4 清单 + 逐文件资源 + 续传 + 可恢复安装

满足本期要求，兼容现有目录结构和 GitHub 发布方式。某个 NPK 改变时下载该文件，其他 NPK 不下载。本机基线含 426 个 NPK，总计约 497 MiB，最大约 23 MiB，逐文件粒度适合先解决可靠性。此数据只描述本机样本，不构成所有玩家安装的大小上限。

### 未选：文件内部块差分

SteamPipe 把文件分块并复用旧块，MSIX 使用块映射和 SHA256。更省大文件的流量，但需额外处理块布局、基线复用、重组和差分失败；资源重新排序或加密也会影响命中率。本期不做，V4 不依赖从某个前置版本连续打补丁。

### 未选：整体替换为 Velopack/MSIX

成熟方案值得参考，但还需要适配现有游戏目录、双架构、PVF/NPK 和玩家配置迁移，不能直接当成免改造的替代品。

直接依据：

- [SteamPipe](https://partner.steamgames.com/doc/sdk/uploading)：内容分块、复用、旁路重建后提交，以及包结构对更新大小的影响。
- [MSIX 差量更新](https://learn.microsoft.com/en-us/windows/msix/desktop/managing-your-msix-deployment-update)：文件/块映射、SHA256、未变内容复用。
- [Velopack](https://docs.velopack.io/integrating/overview)：更新锁、暂存、待安装状态和差分回退。这里不采纳其自动强杀应用的行为。
- [TUF](https://theupdateframework.github.io/specification/latest/)：元数据版本、长度/哈希绑定、一致快照与防回退的设计依据。本期不宣称实现完整 TUF 签名/委托体系。
- [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)：每个 Release 最多 1000 个附件，单附件必须小于 2 GiB；发布工具必须预检。
- [Gitee Releases](https://help.gitee.com/repository/release/create)：普通项目单附件不超过 100M、仓库附件合计不超过 1G；据此采用大文件分卷传输并预检总量。

## 4. V4 文件与发布模型

### 清单与文件策略

线上清单包含独立的 schema、release identity、版本、commit、架构、normal/test 类型、完整受管理文件集、配置迁移及显式删除项。文件至少包含相对路径、64 位长度、SHA256、可信资源定位信息。资源允许嵌套目录与任意扩展名，不硬编码 DLL/PVF 白名单。小文件/空文件也能正确表示。

区分三种策略：

1. **受管理文件**：实际内容必须与目标清单一致，包含选择发布的 EXE、DLL、PVF、NPK、图片、网页等。没有新版本也检查；损坏自动进入修复计划。
2. **保留并迁移的配置**：只校验结构及指定迁移的后置条件，不要求整文件与线上字节一致。
3. **本地运行数据**：日志、账号缓存、截图、存档、更新缓存和备份不被普通资源清单替换或删除。

所有路径必须位于客户端根目录。拒绝绝对路径、上跳、盘符/ADS、Windows 保留名称、大小写碰撞、重复路径及链接/重解析点；安装期间保持目录身份。配置保护不允许通过换大小写或别名绕过。未知本地文件默认保留；移除旧文件需要明确 tombstone，且只能作用于历史受管理文件，操作前备份。

发布预检比较前一目标的完整文件集。旧文件从新清单消失时，必须明确声明“删除”或“保留并解除管理”；没有声明则拒绝发布，避免漏选 DLL/NPK 后让旧补丁残留却显示全量校验成功。解除管理需要在发布预览中显式列出，不从文件遗漏推断。此项是设计审阅后补充的实现默认规则。

目标清单携带覆盖所有受支持旧版本的累计退役记录，配置迁移也提供可重复执行的有序迁移链或完整目标约束，不能只包含相邻版本的差异。从 A 直接升级 C 时，B 中删除的旧 DLL、解除管理的资源和新增端口仍须处理。清单声明支持的基线范围；不支持的旧基线要求桥接，不静默遗漏。累计记录作用于客户端历史受管理集合，不能据此删除原本从未受管理的玩家文件。

### 来源与发布一致性

保留 GitHub 公共下载、无玩家凭据。清单从所配置仓库的 HTTPS 发布元数据取得，GitHub 提供附件 digest 时验证原始清单，清单再绑定每个资源的长度/哈希/附件身份；缓存保存这条来源记录。可信地址及重定向按白名单验证，不接受任意代理下载地址。这里的信任根是预配置的仓库/提供方与 HTTPS，并非离线数字签名。

下载和发布使用 provider 接口，GitHub 为正式源、Gitee 为显式测试源，协议核心不绑定某家 API 的 release ID/digest 字段。Gitee 不假定提供附件 digest；必须从该仓库的结构化附件列表解析同一发布的清单，验证 HTTPS/仓库归属/允许的重定向，固定该清单的字节哈希和发布身份，然后验证各文件内容。不能从发行说明中的任意外链取清单。不同 provider 的 ID 不比较大小；由清单版本、渠道和内容身份判断目标。

2026-11-08 已通过不带凭据的请求确认 Gitee 仓库公开、仓库 API 与发行版列表 API 返回 200，当前无分支/发行版。尚未确认附件下载匿名可用。首次测试发布只放最小来源说明和测试更新资源，不推送私有 Git 历史。发布权限使用本机可用授权；若缺少授权，在已生成可审阅测试产物后再请求所需连接信息，不将令牌放进客户端、URL或日志。

Gitee 的普通项目限制小于现有登录器体积，因此允许把一个逻辑文件拆为不超过 48 MiB 的传输分卷：清单绑定各卷的顺序、长度、哈希，以及最终文件长度/哈希。校验仍以完整逻辑文件为单位；文件需修复时获取其所需分卷，完成的卷可复用，合并后验证整体。这不是文件内部差分，不将旧文件局部内容作为新分卷的基线。

测试客户端显式选择 Gitee 测试仓库/渠道，禁用误回正式渠道的隐式跳转；每次更新固定一个已验证的目标清单。若后续支持镜像，只允许匹配完全相同目标内容的资源替换来源，不能混合两个仓库的“最新版本”。发布后用新建、无 cookie/无 Authorization 的 HTTP 客户端验证清单、资源、分卷续传；遇到登录页/验证码/HTML 必须失败，不能让玩家填写发布令牌。

资源可按内容哈希命名，跨版本复用通过已发布、可读的不可变资源引用实现，不能依赖上一版客户端恰好留有某个 ZIP。每次发布使用新版本和新发布身份；不靠重传同名旧资产修复已发布版本。明确区分主动回退发布与意外旧清单，不将 Release ID 当成文件正确性证明。

先上传全部资源并校验，最后发布主清单/开放 Release。草稿与不完整发布不可被正常客户端选中。删除旧 Release 前，发布工具检查是否仍有清单引用其资源。

按 provider 预检附件个数、单附件大小与仓库累计限制，Gitee 通过上述分卷解决单文件限制；总量或数量仍超限时明确阻止发布并列出问题，不遗漏文件、不擅自删除旧发布或切换存储。不限文件类型不等于规避托管平台容量限制。

### 离线打包 GUI

增加“更新资源”选择：目录扫描、包含/排除规则、受管理文件预览、与上次清单对比、下载体积估算、配置迁移预览。默认排除本地运行数据和私人配置；发布内容由操作者确认的选择决定，不自动上传整个游戏目录。

生成完整目标清单，但只上传尚未存在的资源。x86/x64 的登录器及架构相关依赖分开，共用资源允许复用；normal/test 保持隔离。CLI 和 GUI 使用同一生成/验证逻辑。

## 5. 校验、下载、安装与恢复

### 每次启动流程

恢复未完成事务 → 取得并验证线上清单（或明确使用可信缓存）→ 完整检查所有受管理文件的 SHA256 → 生成变化/缺失/损坏清单 → 下载必要文件 → 安装 → 全部受管理文件再次校验 → 写成功状态 → 开放游戏启动。

文件时间戳/大小只能辅助显示，不能替代用户要求的完整哈希校验。不因“版本号相同”“上次显示成功”或存在 state.json 跳过检查。失败和取消后的下一次启动仍走同一流程。

本地旧清单损坏不阻断获取可信线上修复清单。未知文件不因为不在清单而被删除。校验结果记录具体路径、期望/实际哈希、文件大小与处理结果。

连不上 GitHub：使用最近一次成功验证来源的缓存清单做全文件校验，结果通过且无未决安装事务才能允许离线启动，显示“文件符合缓存版本 X，未确认线上最新版本”。没有可信缓存或本地不完整时不把安装标为可用，明确提供重试/修复入口。

分别保存“已安装且验证通过的版本 A”和“已发现/正在下载的目标 B”。下载 B 不覆盖 A 的清单或可用状态；尚未修改目标目录时，取消/下载失败/离线均可在重新完整验证 A 后继续使用 A，明确提示 B 尚未安装。进入提交阶段后，必须先恢复 A 或完成 B 并校验，不能以缓存 A 为理由放行混合文件。此项按用户允许已验证旧版继续启动的选择细化。

已有自托管 `UpdateServiceUrl` 保留显式优先语义，原服务未提供 V4 时继续走原 V3 协议并明确其能力；不擅自改为 GitHub/Gitee。显式关闭联网更新的本地测试模式保留原本本地校验路径，不要求联网信任记录；若已有 V4 安装则校验已提交的本地清单。任何模式都先处理未完成安装事务。UI 清楚显示当前源/协议/是否停用联网检查，不把关闭更新误报成“线上最新”。V4 的 Gitee 测试配置需要独立显式设置，不能被旧的自托管地址悄悄覆盖。

### 下载恢复

- 持久缓存以 SHA256 和长度标识，已验证完成的文件可跨重启复用；失败不清掉其他成功文件。
- `.partial` 与对应下载身份记录绑定，HTTP Range/If-Range 续传；验证 206 的 Content-Range、总长度及返回长度。服务端忽略 Range 返回 200 时从零重建该文件；416 时先检查本地长度/哈希再决定重启该文件。
- GitHub 临时重定向 URL 过期时从固定附件身份刷新地址；不把临时 URL 当永久标识。
- 完成后流式校验长度与 SHA256，失败只重下该文件；禁止将错误响应页当资源保存成功。
- 区分用户取消、连接失败、读超时、限流、HTTP 错误、校验失败和磁盘错误；有上限的退避重试并尊重 Retry-After。使用连接/无进度超时，不因整个下载超过固定时长就取消正常慢速传输。
- 限制并发，默认少量并发；所有大文件流式处理，支持 x86 登录器的内存限制。
- 进度分别展示校验、下载、安装、复核阶段及当前文件、已完成/总文件数、字节、速度、重试原因；可取消下载，安装提交阶段避免中途半退出。

### 安装事务

- 下载/安装和游戏启动共享安装目录级互斥协调。下载可继续；文件提交前等待占用释放，提示实际进程名/PID，只有玩家明确同意才能结束可终止的占用进程。
- 预估缓存、暂存、备份、同盘临时文件所需空间，不能只检查下载体积。
- 所有新文件下载并验证后才开始修改目标。备份保存当前实际字节和哈希，即使旧文件已损坏，也不因旧清单不匹配而拒绝修复。
- 持久记录新增、替换、删除、配置迁移、原文件是否存在、原内容哈希以及阶段。备份落盘后写事务，再用同盘临时文件替换，目标清单/成功状态最后提交。
- 启动恢复不得依赖尚未完成的混合版本执行游戏。恢复动作验证备份/暂存的身份后继续或回退，不能悄悄丢弃事务。
- 回滚到原本已经损坏的安装，只表示恢复旧字节，不标记“恢复可用”；完整校验不通过仍保持修复状态。
- 安装之后校验所有受管理文件及配置迁移后置条件。仅在通过后显示成功并解除启动限制。
- 完成缓存可按预算清理，未决事务和必需恢复资料不可清理。日志、缓存、备份各有独立保留上限。

### 旧版迁移与修复入口

先用现有 V3 能识别的桥接包升级登录器，再由新登录器使用 V4 清单完成资源管理。保留 x86/x64、normal/test 的桥接与验收。不改变既有已发布资产。

旧版若因安装损坏而根本无法更新，提供完整桥接/独立修复入口。登录器自身损坏到无法执行时不能靠它自修复；修复入口必须能独立启动并使用相同来源验证与事务引擎。具体二进制组织由实现阶段决定，不能只做一个再次调用损坏登录器的脚本。普通更新不能要求玩家每次下载整合包。

## 6. 配置增量迁移

迁移以唯一 ID、目标文件、结构化操作和后置条件定义，不执行远程脚本，不做字符串全局替换。首批支持端口集合合并、缺失字段补默认值，以及带旧值条件的字段转换。

示例：对 `launcher.json` 的 `Relay.TcpPorts` 确保存在 7110/7111/7112。保留自定义端口，合法范围校验、去重；账号、密码、服务器列表、所选服务器、地址、IPv4/IPv6 偏好、窗口设置和未知扩展字段均保留。现有省略的默认端口先按该版本默认语义展开，不能让新增集合挤掉默认登录端口。

迁移幂等；重复执行不重复添加。每次校验检查必要后置条件，不仅检查迁移 ID。配置已经由玩家修改时按字段规则合并；配置格式损坏时保留原始文件并提示修复，不用线上空配置覆盖账号。

配置写入和迁移记录加入同一安装事务，回滚一起恢复。与账号/设置窗口写入使用同一锁及最新磁盘快照，防止拿旧内存配置覆盖新迁移。配置本身不进入“必须和线上完全一样”的二进制哈希策略。实际出现其他格式如 launcher.txt/INI 时，通过对应解析器和声明操作支持，不假定它与 JSON 同结构。

## 7. 按事件保存故障报告

位置：`Logs/DFLegacy/Incidents/`，文件名含本地日期时间（毫秒）、PID、事件 ID，跨线程/多开不覆盖：

- `error-*.log`：启动失败、配置异常、账号请求错误、更新失败等。
- `networkerror-*.log`：中继异常绑定/连接、超时、意外断开，以及可确认的原生游戏断线。
- `crash-*.log`：原生未处理异常、已确认崩溃或游戏异常退出；注明证据类型，未知退出原因不捏造异常码。
- `update-*.log`：每次校验/下载/安装的摘要和逐文件结果，成功也保存；失败的 error 报告关联该更新 ID。

每份报告包含版本/commit/架构、安装目录、会话与事件 ID、故障时间/时区、阶段、错误码、异常链/调用栈及相关前后文。日志留近期环形上下文，事故发生时快照到单独文件，主日志继续保留。网络报告包含协议、方向、端口、连接 ID、耗时、收发字节和 Socket 错误码，敏感凭据/请求体不记录。重复错误合并计数，设置按数量/大小/时间的保留策略；默认不自动上传。

用明确事件分类而非匹配日志里的“error”字符串。正常退出、取消更新、频道切换时的预期连接关闭不是网络事故。短时重试失败可记录在单份事件中，不生成几千份日志。

普通版补最小原生现场记录：在异常点保存必要的地址/寄存器/模块/栈信息，再结合未处理异常/已验证的崩溃处理入口/进程退出信息定性。可以处理的 SEH 探针异常不得直接标成崩溃；不吞异常或伪造继续运行。挂接原生位置需验证目标二进制与指令签名，不支持时回退到明确标为“缺少原生现场”的退出报告。

当前独立抓取工具可作为“详细崩溃采集”的选项整合；普通启动不默认附加调试器。需要 DMP 时从独立进程采集，明确保留位置与大小上限。对于 CrashSender 弹窗但进程仍存活的情况，应验证原生报告入口；在该入口尚未验证前只能使用详细采集，不能宣称默认崩溃报告已覆盖这种情况。

原生断线须覆盖本机中继与直连：中继用结构化终止原因；直连通过已验证的原生连接失败/断线通知入口产生事件。不得把底层一次短读、WOULDBLOCK 或正常频道切换误判为掉线。

校验本身无法修复服务端功能。诊断中明确客户端版本/PVF 身份，服务端版本只在接口实际提供时记录，否则标未知，不推断与客户端一致。

- 每次启动、同版本损坏、缺失文件、混合版本、旧清单损坏：最终逐文件哈希正确；网络请求证据证明未变化文件未下载。
- NPK/PVF/DLL/EXE/嵌套路径/空文件；x86/x64 与 normal/test 不串线。
- 慢网、断网、程序退出、重新打开、Range 200/206/416、临时地址失效、429/5xx、截断、哈希错误；已完成缓存不重复下载。
- 下载后目标被改、替换到一半强杀助手、写状态时中断、备份损坏、空间不足、文件占用、多开；不运行未验证混合版本，恢复或失败状态真实明确。
- 配置端口新增、已有自定义端口、缺省字段、未知字段、账号设置并发保存、重复迁移、迁移失败/安装回退；原账号与地址保留。
- 离线可信缓存完整可启动并提示；损坏/无缓存不可冒充已验证。重新联网后仍检查线上目标。
- 事故日志名称唯一、关联上下文、敏感信息脱敏、保留上限；正常退出/频道切换/取消不误报；模拟原生未处理异常及异常退出，分别验证证据分类。
- 旧 V3 → 桥接 → V4 → 人为损坏一文件 → 只修复该文件，全流程本地 HTTP 故障模拟、真实 GitHub 只读下载和已授权 Gitee 测试发布验收。Gitee 包括 x86/x64、大登录器分卷、无凭据下载及资源复用。正式 GitHub 发布和线上替换另行执行。
