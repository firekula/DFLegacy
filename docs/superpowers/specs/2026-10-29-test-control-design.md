# 隔离测试 CLI 与 debug 控制接口

用户于2026-10-29确认：先实现仅测试环境可用的 CLI/debug 接口、补测试，再恢复四客户端掉落验收。以服务端提交和持久化为准，客户端核对同步，仅关键界面截图。位置修改、指定敌人秒杀、指定掉落集中与其他掉落移开均已明确授权。

## 行为与边界

- 默认关闭；服务端 `Debug.TestControl.Enabled`、客户端 `[DebugOverlay] EnableTestControl=1` 均须显式开启。CLI不能替用户开启正常服务配置。隔离运行沿用独立服务、存档、客户端配置和进程身份绑定。
- `state` 同时返回服务端房间/成员/敌人生死/掉落/已提交背包及客户端位置/HP/生死。每个字段标明来源；服务端没有的实时客户端状态不得推断。
- `player teleport` 在当前地图设置指定角色位置。由匹配PID/启动时间/UID/地图代次的客户端在游戏线程执行，核对本机及队友位置；不把本机执行完成称为全队同步成功。
- `monster kill` 指定原生敌人UID，通过经过验证的原生死亡/上报路径进入既有服务端击杀、掉落、经验和清场流程。重复执行不重复结算。与正常战斗能力验收分开标注。
- `drop isolate` 将指定现存groundId移至指定角色脚下，其他现存掉落停放到另一位置。保留groundId、物品实例、品质、来源、路由与拾取状态；禁止在拾取处理中搬移。服务端原子更新布局，CLI协调所有同房客户端并分别核对，失败明确标部分同步，不删除重发来伪造移动。
- `loot result` 等待服务端最终 `committed/rejected`，包含run/room/ground/pickup、拾取者、得主、骰分、槽位、物品实例及拒绝原因。选择得主或收到命令不是提交。存档成功后才能发布committed；发送/客户端同步另列。
- CLI返回结构化JSON及区分成功/拒绝/超时的退出码。无隐式截图、无外部鼠标键盘控制、无任意地址写入命令。原游戏资源及正常存档不修改。

## 选择的实现

沿用现有本地文件邮箱、后台IO和游戏线程分工，增加服务端测试快照、短期测试租约、原生受限命令与统一Python CLI。纯客户端修改无法证明服务端入账；纯服务端坐标修改不足以驱动ACT1本人的原生演员，因此采用两端协调。用户已确认这一方案，日常业务协议和入账规则保持原路径。

服务端每次启动生成独立nonce；租约绑定run/UID并短期过期。命令绑定进程启动时间、客户端代次、地图、请求ID和nonce，防止换房或重启后执行旧命令。游戏线程不读写文件。测试关闭时不启动控制IO或执行修改。

原生命令固定112字节，小端`<4sHHIIQQQQQQIIIIiiiiQQ`：DLTC/version/size，PID/UID，启动时间/请求ID/发出tick/快照tick/代次/序列，actor/map/user/op，target/x/y/reserved，nonce/run。操作1=本机角色定位，2=敌人死亡，3=现存ground定位，4=目标ground定位并将其他ground放到停车点。操作4的reserved低16位／高16位分别编码有符号停车x／y，其余操作reserved必须为0。租约40字节`<IIQQQII`：DTTL/version/nonce/run/filetime/UID/flags。所有原生调用必须验证目标ACT1原始映像和对应函数签名，不猜地址。

服务端快照`dfdebug-test-server.json`；服务端布局命令及结果使用独立JSON邮箱；原生每PID命令与结果为`dfdebug-test-control-{pid}.bin/.json`。CLI消费明确schema、时间和身份，不能读取过期文件冒充当前结果。

原生独立地面快照为`dfdebug-test-state-{pid}.json`，schema `dfl-client-test-state/v1`，绑定进程、UID、代次、地图、run和nonce，含明确valid/truncated及每件物品的原生位置、ID、active/pending。约200ms采样，总地图对象上限256，超过范围显式拒绝，不把部分列表当作完整同步。支持原版允许的NULL描述对象，不据此推断它一定是金币。
