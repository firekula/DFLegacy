## Approaches

- 将全部功能并入 `ijl15.dll`：兼容现有安装器和更新器，工作量较小，但仍替换原版 DLL。用户没有选此路线。
- 登录器加载独立补丁 DLL：保留游戏原有二进制，明确区分游戏与补丁；需要新增启动引导、版本一致性校验和旧版迁移。用户选此路线，先做隔离验证。
- 改成另一个系统 DLL 的同名代理：仍依赖搜索顺序和导出转发，未消除替换／代理问题，不采用。

## 正式结构与启动

以下为实现建议，由本次设计确定，不声称已通过原型验证。

- 新原生目标 `DFLegacy.Client.dll`；它承载现有日常补丁，不导出或替代 IJL 编解码接口。
- 32 位启动引导程序内嵌在单文件登录器中，按版本提取到 `.dflegacy/runtime/`。根目录不增加辅助 EXE。
- 登录器仍为现有 Windows x64 WPF 程序；32 位引导仅启动本次选择的游戏子进程，不接受任意已有 PID。
- 引导使用宽字符进程创建与 Detours。在正式实现中，DLL 路径解析必须支持中文与空格，并验证最终加载路径，不能默默回退到系统搜索到的其他 DLL。可用受控 ASCII 文件名与游戏目录定位；具体机制由实现者选择并用中文路径夹具验证。
- DLL 的 `DllMain` 只做必要的引导工作。补丁初始化在加载器锁之外、游戏原入口执行之前完成；具体入口跳板由实现者选择，必须有原生夹具覆盖失败和恢复。原型直接沿用旧 DllMain，只证明可加载，不能原样作为正式实现。
- 启动器校验补丁及引导的架构、版本和哈希，维持文件身份到加载完成。子进程通过仅限本次启动的本地通信报告 PID、进程创建时间、模块路径、版本及初始化结果。失败或超时关闭本次子进程并显示原因；禁止“进程创建成功”被当成“补丁加载成功”。
- 不更改游戏工作目录；保留登录参数、中继生命周期、启动观察、显示设置与服务地址配置行为。日志不写账号、密码或完整启动参数。
- DLL 代码可以保留内部旧命名以降低改动，但用户提示和日志使用独立补丁名称。

## 普通功能与调试功能分离

生产功能由一个运行时拥有，普通包与测试包使用同一份核心：现有分辨率／缩放、鼠标滚轮、FPS 显示、频道／组队／副本修复等，以及从 Debug 移出的城镇右键寻路、跨区域路线和地图点击反馈。

迁移不只复制 CPP：需要把状态采样与 `ExportState` 解耦，把每帧更新、工作线程及 hook 的初始化／释放归属固定下来。关闭调试导出不能停止寻路；装上 debug.dll 不能重复安装同一 hook、重复采样或重复执行路线。

`debug.dll` 保留诊断浮窗、状态导出、性能记录、测试命令入口等调试能力，通过有版本的接口使用共享运行时。普通包不含、不自动加载 debug.dll；目录中残留旧 debug.dll 也不能因存在就启用。

测试包默认开启本地诊断能力，自动输入、组队文件命令和其他会驱动游戏操作的测试控制仍需显式配置，不随复选框自动启用。客户端本地诊断可独立工作；依赖服务端共享目录的覆盖信息仍明确显示是否有数据，不声称支持远程目录自动同步。

## 旧安装与自动更新迁移

旧更新器只接受 schema 1 的登录器＋ijl15.dll，不能直接给它塞入新 DLL。独立审阅还确认：旧更新器不检查当前 IJL 是否为替换版，桥接附件也会覆盖玩家自行恢复的原版 IJL，新登录器事后才启动，无法阻止。

**本次建议：旧登录器需要手动迁移一次，以后恢复自动更新。** 这是守住原文件保留边界的取舍，需随本文确认；不声称旧更新器可以无缝自动迁移。

1. 独立补丁发行版不再发布旧 schema 1 附件 `DFLegacy-client-update-win-x64.zip`。旧用户从工作台下载新版玩家包，或从 GitHub 下载不含私人服务器配置的新版完整普通／测试客户端工具包；包中只有本项目文件，不含 ijl15.dll。覆盖新版登录器、增加独立补丁后，再运行迁移检查。工具包不含 launcher.json 或 Config.ini，以免手动覆盖玩家设置。发行说明与下载说明把这一步放在开头。既有已发布旧附件保持原状，不追溯修改发行记录。
2. 新登录器使用单独的 schema 2 附件。普通与测试包分别命名，例如 `DFLegacy-client-update-v2-win-x64.zip`、`DFLegacy-client-update-v2-test-win-x64.zip`。普通严格更新登录器＋独立补丁，测试额外更新同版 debug.dll；不能用普通附件更新测试核心后遗留不匹配的 debug.dll。
3. schema 2 清单包含 flavor、版本、commit 与固定文件列表，延续下载完整性、路径限制、备份、事务日志、回滚及重启验证。安装清单作为受控事务元数据与两个／三个二进制同步更新或同步回滚，避免旧清单配新 DLL；只从验证后的更新清单生成，不接受附件自带的任意额外安装路径。更新不触碰游戏原有二进制和玩家配置。不得静默降级到 schema 1。
4. 旧目录已安装替换 IJL 时，切换独立模式前必须恢复用户自己持有的原版 IJL。**不能因为文件叫 ijl15.original.dll 就认为它是原版**：实机该文件事实上是一份旧补丁，而 ijl15.dll.bak 才与原版匹配。
5. 提供一次清楚的迁移提示，列出当前文件和已验证备份。用户确认后，先备份当前替换 DLL，再恢复验证通过的原版；没有可验证备份就让用户选择自己持有的原版文件。取消则不修改，停止这次游戏启动。不能让两个补丁同时接管游戏。
6. 已知替换版本用发布时积累的哈希／受控标识识别；未知 IJL 不擅自覆盖，不按文件大小猜测。原版兼容判定覆盖已验证哈希及所需导出／架构，扩大支持需验证。迁移失败恢复到迁移前状态。

对新安装承诺“原文件不覆盖”；旧安装的恢复操作是用户可见的一次性修复，不能称为“从未改动过原文件”。不增加偷偷使用旧 IJL 模式的回退。若用户希望旧版本自动升级，应另行确认接受旧更新器的备份／覆盖行为，不能与这里的边界混称。

## 日志与旧文件整理

- 登录器、补丁、诊断模块的日志集中在目标客户端 `Logs/DFLegacy/`；渲染诊断位于其 `render-diagnostics/` 子目录。登录器还未解析出有效客户端目录时才使用登录器自身目录下的 Logs。
- 原游戏日志继续使用 `Logs/`；补齐已确认原生日志的重定向。`rs_log.txt` 必须先确认实际写入点再处理，不能对所有 TXT 文件做通用重定向。
- 原生模块统一使用宽字符日志路径工具，并自动创建所需目录。日志失败不导致游戏崩溃；不能退回根目录制造散文件。启动器给出可读提示；无可写日志位置时允许诊断不可用，但不能把它报告为正常记录。
- 诊断读取先读新路径，兼容只读旧路径。截图仍在 ScreenShot，配置仍在原处；`.dflegacy` 更新事务、回滚备份和调试控制目录不属于日志，不能为整洁而盲目搬迁。
- 对以前生成的日志做可重试的归档：仅匹配确认属于本程序的固定文件名／PID 日志模式，移入 `Logs/DFLegacy/legacy/`，同名不覆盖；被占用、路径链接或身份不符的文件跳过。旧 render-diagnostics 只处理已知诊断文件，不移动整个未知目录。原游戏日志按明确清单归入 Logs；不自动删除日志，不扫描搬走任意 JSON/TXT。

## 验证与发布条件

1. 导出普通／测试包：默认模式、bool 校验、可选调试资产缺失、错误哈希／版本、隐私过滤、根目录布局与安装说明。
2. 原生启动夹具：初始化先于游戏入口，错误架构／未知代码拒绝，DLL 不存在或被改动，中文空格路径，超时、失败与父子进程退出；原有文件哈希始终不变。
3. 游戏回归：普通包无 debug.dll 时测试右键寻路、跨区、点击反馈、显示缩放、频道和已有游戏修复；测试包再启用诊断，确认没有双 hook、双命令及普通模式残留加载。
4. 实机客户端回归使用匹配 PVF，包含登录、洛兰进出及回城；记录原始 EXE／IJL／PVF／NPK 哈希。原型不替代此项。实际桌面操作沿用用户的控制权，之前停止的桌面自动化不自动恢复。
5. 旧版手动迁移和 schema 2 普通／测试更新、备份恢复、缺失原版的迁移提示、拒绝更新、崩溃回滚、玩家配置保留，均需专用夹具。确认新版发行不产生旧更新器可消费、会覆盖原版 IJL 的桥接附件。
6. 全部新写日志位于约定目录；旧日志归档不覆盖、不吞配置，不把更新状态／命令文件搬走；不能写日志的情况有可验证的退化行为。
7. Windows 原生与登录器测试、Linux 管理器／导出／发布工具测试、各 RID 包及 Docker 检查通过后，才从同一源码版本发布。GitHub 继续用脱敏快照同步源码，Release 元数据保留实际构建来源映射。

## 不在本次范围与实现者可决定事项

不修改原始旧壳的现代 Windows 行为，不重新发布游戏 EXE／原版 IJL，不改变 PVF/NPK，不重写渲染 API，不扩大调试命令的默认权限。独立加载器只负责自己的游戏子进程。

实现者可决定内部目录、类名、共享运行时 API 细节、日志同名后缀和测试夹具组织，但不能改变普通包完整功能、原文件保留、旧版迁移可见、测试包版本一致及明确拒绝旧壳这几条行为。
