# 官服玩法面「证据链工程」设计

> **日期**：2026-10-05
> **来源**：与项目所有者的设计对话（brainstorming），五节设计逐节获批后落成此文
> **这份文档是什么**：一份**证据链工程的规格**——规定"为了让按官方架构重写有硬证据，要采哪些证据、按什么单元采、怎么验、按什么顺序"。
> **它不是什么**：不是实现计划（那是下一步 `writing-plans` 的产物），也不含任何代码。
> **读者**：未来执行这件事的会话/人（必须能脱离对话历史独立读懂），以及项目所有者（评审门）。

## 0. 目标与三个已定决策

**总目标**：让"按官方版本复刻"这件事的每一处依赖都有**可重跑、可证伪**的证据，而不是"看起来对"。

三个由项目所有者定下的决策（**不再讨论**）：

| # | 决策 | 含义与后果 |
|---|---|---|
| D1 | **玩法面走"重推导"** | 以 `df_game_r` 的符号表与 `.idb` 为准重建**行为规格**；现有 DFLegacy 实现**只用于排优先级与对照，不作为证据**（它的"能跑通"是 `[真机]`，但它是同源材料，不能拿来自证） |
| D2 | **达标线 = 与现有 DFLegacy 功能等价** | 以 `STATUS.md` 的功能清单与真机验收矩阵为**对照表与回归集**；"官方有、DFLegacy 没有"的内容进**待评估队列**，不自动纳入 |
| D3 | **真机攒批** | 客户端**启动可自动**（`--headless --account X`），**游戏内操作要人**；因此 `[真机]` 验收按里程碑攒批次，不进单元的关键路径 |

**下游约束（来自既有计划，未变）**：新分支替换现有 DFLegacy 服务端、**客户端不改**、追**架构级仿制**（进程拆分、配置、启动方式、日志目录都仿官方）。

## 2. 阶段一（M0）· 工具层与分母

**目标**：把"我们知道我们不知道什么"变成**可计算的分母**，并打通 `df_game_r` 的静态通道。
**边界**：本阶段**不写任何行为规格**。

### 2.1 产物五件

| # | 产物 | 内容 | 生成方式 |
|---|---|---|---|
| 1 | `demangled-syms.tsv` | 352,694 个符号名字可读（保留 addr / size / type） | sidecar `c++filt` 批量（已验证可用） |
| 2 | `catalog_dispatchers_full.txt` | **全量** `Dispatcher_*` / `DisPatcher_*` 家族 + `process` / `dispatch_sig` 地址与**真实 size**，按命名族分类 | 从 (1) 抽；`nm -S` 真实 size；现有 84 条子集作对照 |
| 3 | `catalog_handlers_full.txt` | 处理器目录（现文件为空） | `dispatch_sig` 调用图 + `packet_senders.txt` 的 1248 个 `put_header` 点 |
| 4 | `opcode-map.tsv` | `CMD 0..607`、`NOTI 0..562` **每一条** → 派发器/处理器，或明确标注"无派发器 / 未使用 / 服务间" | `opcode_cmd/noti.txt` 的 `.rodata` 地址 → 查表代码 → 家族 |
| 5 | `.recon` 申报两个工具 | `demangle-catalog`（sidecar `c++filt` 包装）、`ida-game`（对 `df_game_r.bin.idb` 跑 IDA，走 `run-ida.sh` 的 `DNF_IDB=` 覆盖） | 按 `recon-tool-registry` 写 caveats：IDA **单写**、170 MB 库加载分钟级、sidecar **只可用于 CPU 任务**（其 netns 可能已失效）、爆炸半径逐条写清 |

### 2.2 验收：四条可证伪判据

> **先说清它们的"独立性"**（避免把同源材料当两份证据）：
> 判据 2 与 3 **都是同源交叉** —— 输入都来自同一张 `.symtab`，它们验证的是**提取与分类有没有出错、有没有漏**，
> **不验证符号表本身**。真正碰到二进制另一面的是判据 4（反查 `.rodata` 里实际注册的名字串）。
> **四条里没有一条能单独证明"目录是全的"** —— 合起来把"漏"的概率压到可接受，这是这一节能给的最强承诺。

1. **命令映射无余数**：608 + 563 每条号都有归属或明确标记，**不接受"未解释"**；
2. **两个 demangler 结果一致**：sidecar `c++filt` 与 IDA 各自 demangle 后，`Dispatcher_*` 集合差异**逐条解释**（验的是解名与提取，不是符号表）；
3. **模块清单交叉**：`*Dispatcher*.cpp` 的 `FILE` 条目数 vs 目录家族数**同量级**，且每个家族能指到所属 `.cpp`（同一张表的另一个视角）；
4. **抽样反证**：随机抽 10 个家族，用其 `dispatch_sig` 地址反查 `.rodata` 里它注册的名字串，**必须命中**（这一条才真正独立于符号表）。

### 2.3 预写的失败模式

若判据 1 出现**大量"无归属"**命令 ⇒ 说明注册**不是静态表**（可能运行期构造）⇒ **就地改判**为运行期观测：对官服容器读它启动后实际注册了什么（`[回放]` 层顶上）。
**这条预写的意义**：不让"静态查不到"被误读成"这条命令不存在"。

## 3. 阶段二 · 工作单元与规格模板

### 3.1 单元是什么

**一个"功能面" = 客户端上能观察到起止的一条流程**（登录、选角、城镇、单刷一副本、结算、组队、交易…）。
**不是**一个派发器——派发器是**清点用的库存**，流程才是**可验收的单位**。

**粒度准则**：单元内命令数落在 **~10–40**；一份规格读不完、或一次真机会话验不完 ⇒ 切分。
**偏离要写明理由**（试点单元可能只有 1–2 条命令；交易类可能远超 40）—— 准则的作用是防止"一个单元吞掉半个系统"，不是拿来卡合法的小单元。
**反向约束**：跨单元的命令必须**互相显式引用**，否则会漏。

**⚠️ 端口按世代换位来写**（既有结论，容易踩）：2008 客户端的**握手在 2311、登录+玩法在 7001**；官服那代是**7001 握手、30011 游戏**。
⇒ 单元规格里凡涉及端口，一律注明**是哪一代的哪个端口**，**不许把官服的 7001 直接抄成我们的 7001**（`SPEC-login-to-channel.md` §2.1 换位表）。

### 3.2 单份规格模板（六件套）

| # | 部分 | 内容 | 判据 |
|---|---|---|---|
| 1 | **范围声明** | CMD/NOTI 号清单（含方向）、涉及的派发器/处理器地址、参与的进程、**显式排除**的相邻命令 | 命令清单**必须**来自 `opcode-map.tsv`，不许手写 |
| 2 | **线上契约** | 逐命令：字段名/偏移/宽度/字节序/取值域/填充；变长规则；是否走 AES+zlib 那条路 | 每个字段都要有来源（`.rodata` 结构串 / 伪码地址 / 抓包样本） |
| 3 | **状态机 + 失败码** | 前置条件、允许的下一步、**官方失败码与日志串**、超时/重试、幂等性 | 这是重推导**唯一**只能从官服拿到的东西 |
| 4 | **跨进程与持久化** | 哪些状态跨进程一致（谁裁决）、写了哪些表/字段、失败回滚边界 | 与 `STATIC-FINDINGS.md` §5.3 的边界证据对齐 |
| 5 | **证据台账** | 每条结论 → 证据类别 + 地址/文件 + **可重跑命令**；`[推断]`/`[未验证]` 单列并写"怎么才能验" | **不允许出现无来源的句子** |
| 6 | **验收清单** | 三层：`[静态]` 地址 → `[回放]`（官服靶/自研靶）→ `[真机]`（批次用：进哪个界面、点什么、看什么日志/帧） | 每条 `[静态]` 结论**至少**有一条可重跑命令复现 |

### 3.3 "单元完成"的四条件

① 六件套齐全；② 范围声明里每条命令都有布局与归属；③ 台账里每条 `[静态]` 结论都有**可重跑命令**；④ 真机清单已写进批次（**不要求已执行**——真机攒批，不该卡单元收尾）。

### 3.4 两条边界政策

- **阶段一暴露的"官方有、`STATUS.md` 没有"的系统**：进**待评估队列**，不自动纳入（D2），由评审门处置。
- **单元内的"官方行为未知项"**（伪码读不出、抓包也没有）：**不阻塞**单元收尾，但必须进台账标 `[未验证]` 并写"怎么才能验"。

### 3.5 模板已用"登录/频道链"验过

把它套进六件套能对上现有产物：范围声明 = `SPEC` §5.2；线上契约 = §5.1 + §3.4/§3.5；状态机与失败码 = §6.4 + 两条拒绝路径；跨进程 = §4 边界表；证据台账 = `open-questions.md`；验收清单 = `RESUME.md` §3。
**唯一当时没做的是"范围声明来自 `opcode-map`"**（那时还没有这张表）—— 这正是 M0 要补的。

## 4. 验收与真机攒批

### 4.1 三层各验什么（不许越权、不许互相冒充）

| 层 | 验的对象 | 判据 | 频率 |
|---|---|---|---|
| **L1 `[静态]`** | 我们对 `df_game_r` 的**读法** | 每条结论配一条可重跑命令，输出与规格逐字段 diff | 每单元必做 |
| **L2a `[回放]` 官服靶** | **"官方伪码的读法"对不对** —— 用驱动器扮 2012 客户端打官服容器 | 失败码/日志/状态迁移与我们读出的一致 | 每单元必跑（分钟级、无人） |
| **L2b `[回放]` 自研靶** | **"我们现有实现的行为"** | 与 L2a 的**差异表**逐条判定"照官服 / 照 2008 / 两者都行" | 每单元必跑 |
| **L3 `[真机]`** | **客户端在真实时序下的行为** | 批次清单逐条通过/失败 | **每里程碑一次，人工批次** |

⚠️ **两个靶子不许混**：L2a 出"官方服务端行为"，L2b 出"我们实现的行为"，L3 出"2008 客户端的期望"。
**任一被当成另一个用，整条证据链就废了。**

### 4.2 让 L2 成为可能：驱动器（M1 的**前置**，不计入单元数）

> **它在哪一步建**：不是 M0 的产物（M0 是纯静态），而是 **M1 开工的第一件事**。
> **门**：驱动器的自检不通过，M1 的 L2 **一条都不许跑**（触发 **S3**）。

- **通道面（7001）**：沿用已跑通的路子（容器内 `bash /dev/tcp` 发帧 + 密文回宿主解）。
- **游戏面（30011）**：需要一个**最小客户端驱动器**；技术前提**已实测成立**（见 §1：容器 gate 私钥 = game 公钥 ⇒ 我们能自己签一个官方游戏服会接受的令牌）。
- **在哪跑**：**在容器 netns 内跑**（与 7001 注入同一做法）⇒ 绕开宿主端口发布落差（`30011` 被发布成宿主 `30021`）。**若必须在宿主跑，先补 `30011→30021` / `31011→31021` 转发**，否则连的是空气。
- **驱动器要两套方言**：`官服方言`（2012 客户端，供 L2a）与 `2008 方言`（供 L2b）。**不许让一个驱动器同时说两代**——那会把世代差异藏进代码里。
- **自检要求（硬）**：驱动器上线前必须先在**已知答案**的序列上复现（7001 的 `11/5/9/1`，有抓包作对照）。复现不了 ⇒ 触发停止条件 **S3**。

### 4.3 批次编排模板（L3，人的操作只发生在这里）

`前置` 环境互斥决策（容器 or 自研栈在场）→ `启动`（`--headless --account X`，可自动）→ **`人机清单`（动作 → 期望界面/日志/帧 → 判据）** → `采集` → `收尾`（恢复环境、探针退役）。

**多 actor 纪律**（组队/交易/决斗类单元必用）：

1. **actor 标识用会话/进程 id，不用角色名**（重名、改名、换角色都会毁掉归因）；
2. **一个共同零时刻**；
3. **每 actor 一个文件**（`netdump-<pid>.log` / `server-party<N>.log` 已是此形状），**绝不把两个客户端写进同一文件再靠 grep 分**；
4. **每条日志能回答四问**：谁 / 何时（相对零时刻）/ 第几步 / **为什么**（服务端"跳过/拒绝/降级"的**判定结果**）；
5. **预期清单来自范围声明**：批次分析必须输出三栏 —— **预期到了 / 预期没到 / 预期外来了**（后两栏只有清单能发现）。

### 4.4 节奏与硬停止条件

- **一个里程碑 = 2–4 个单元**；里程碑末一次 L3 批次。
- L2 每单元必跑；差异表**不许留"未判定"**（`[未验证]` 允许，但必须写"怎么才能验"）。
- **硬停止**：某单元在 L2a/L2b 都不一致且无法判定 ⇒ 停，先解决（通常意味着**前置环节**就理解错了）。
- **失败即推翻**：L3 失败 = 规格被推翻，按纪律标 `[作废]` 并指向推翻它的证据（不删原文）。

## 5. 里程碑与顺序

### 5.1 排序原则

三条同时成立才排前面：**依赖在前**（会话是一切前置）、**现成对照物最全**（有真机验收矩阵可当回归集的先做）、**正在流血的最先**（当前实现已失败且有可复现样本的）。

⇒ **第一个试点单元 = `STATUS.md` §3.9 的玩法 UDP 应用层 CRC/密码**（19 B `mt` 载荷有原始样本，`df_game_r` 有对应处理器与密码代码）。修好它既是收益，也是整套方法的**第一份成绩单**。

### 5.2 里程碑表

| # | 里程碑 | 单元（功能面） | 真机批次 |
|---|---|---|---|
| **M0** | 工具层与分母（§2） | 非功能单元 | 无（纯静态） |
| **M1** | 会话面 + 玩法 UDP 密码/CRC | **前置：驱动器 + 自检通过（§4.2，不计入单元数）**；单元：①UDP `mt` 应用层（试点）②登录/鉴权 ③角色列表与选角 ④进入城镇 | 一次（单人） |
| **M2** | 城镇面 | ①位置同步 ②同屏可见性 ③附近聊天 ④对端端点表/UDP 打洞 | 一次（双人） |
| **M3** | 单人副本 | ①进图与房间状态 ②清房/怪物判定 ③掉落生成与归属 ④结算与退出 | 一次（单人） |
| **M4** | 角色成长 | ①物品/背包 ②装备与属性 ③技能与加点 ④任务 | 一次（单人） |
| **M5** | 经济与其它 | ①商城 ②邮件 ③宠物 | 一次（单人） |
| **M6** | 社交 | ①好友 ②黑名单 ③在线状态 | 一次（双人） |
| **M7** | 交易 | ①交易生命周期 ②锁定/确认 ③取消/掉线/换区（**§4 的 V8–V12 即现成验收清单**） | 一次（双人） |
| **M8** | 组队 | ①队伍生命周期 ②邀请/应答 ③成员状态与位置 | 一次（双人） |
| **M9** | 组队进副本 | ①组队进图同步 ②房间/怪物状态同步 ③掉落分配 ④中继与 MTU | 一次（双人，最重） |
| **M10** | 决斗 / PvP 数据 | ①决斗请求 ②数据同步 | 一次（双人） |

**顺序理由**：城镇 → 副本 → 成长 → 经济/社交 → 交易 → 组队 → 组队副本 → PvP 是**依赖链**。交易与组队排后面不是次要，而是它们的真机验收**必须双客户端**、成本最高。

### 5.3 每个里程碑的产出与退出判据

**产出**：2–4 份六件套 + **L2 差异表**（每单元一张）+ **一次 L3 批次报告**（含三栏）+ 目录与台账增补。

**退出判据（全为真才进下一个）**：
1. 每个单元满足 §3.3 的四条件；
2. L2 差异表**无"未判定"**；
3. L3 批次报告已归档，失败项按纪律标 `[作废]`；
4. `opcode-map.tsv` 的覆盖状态更新；
5. **评审门**：处置待评估队列，决定下一个里程碑是否调整。

### 5.4 总工作量：M0 结束时重估（不打保票）

现在不给"总共多少段"的数字 —— **分母还没有**。M0 退出时给出真实分母（多少派发器家族 / 608+563 里多少条客户端可达），那时才谈总工作量与里程碑是否需要合并拆分。现在能确定的是量级：**数十段**，M0–M1 是其中最便宜、收益最直接的两段。

### 5.5 实施计划的边界（**这份 spec 不直接变成一份大计划**）

本 spec 覆盖**整个工程**（M0–M10），但**实施计划只为 M0 + M1 的驱动器前置**出一份：
`writing-plans` 的产物是"M0（工具与分母）→ M1 驱动器自检通过"这一段的可执行计划。
**后续里程碑在各自评审门（§5.3 判据 5）之后再出各自的小计划** —— 理由是 M0 会给出真实分母，
现在给 M2–M10 排细计划等于在错误的规模上做排期（这正是 S2 要防的事）。

## 6. 风险与停止条件

| # | 风险 | 缓解 |
|---|---|---|
| 1 | **分母比预期大得多**（可能数百家族，工作量翻倍） | M0 先出分母再谈总量；超出预期走 **S2** |
| 2 | **注册不是静态表**（运行期构造） | 预写改判：转运行期观测（读容器启动后实际注册了什么） |
| 3 | **伪码 ≠ 行为** | 纯伪码结论一律 `[静态]` + 给"怎么才能验"；L2a 作独立验证 |
| 4 | **驱动器自己就是逆向产物**（错了污染所有 L2 结论） | 上线前在**已知答案**序列上自检；两套方言不许混；结论可追到原始字节 |
| 5 | **不能污染靶子**（官服容器是跑着的完整栈） | 只读优先；写操作显式列出并用可丢弃账号；探针命名可识别、用完退役；互斥由脚本管 |
| 6 | **证据通胀**（单元多，易补合理推测） | 台账是硬门：无来源句子 = 单元不算完成（**S5**）；评审门抽查 |
| 7 | **范围漂移**（M0 冒出官方独有系统） | 待评估队列 + 评审门，不自动纳入 |
| 8 | **基础设施重复出血**（权限/npipe/netns/日志截断/端口互斥） | M0 固化成脚本 + runbook（`RESUME.md` 是雏形） |
| 9 | **真机批次变成人工摸索** | 批次清单写到"动作→期望→判据"；**批次前先用 L2 预跑**，把已知会失败的排除在人工环节外 |

**硬停止条件**：

| # | 触发 | 处置 |
|---|---|---|
| **S1** | 某单元 L2a/L2b 都不一致且无法判定 | 停，先解决（通常前置环节就错了） |
| **S2** | M0 分母显示客户端可达命令远超预期（如 >2×）且不愿扩大投入 | 停在 M0；重推导缩为高价值单元，其余沿用现有实现 |
| **S3** | 驱动器不能复现已知答案 | **冻结所有 L2 结论**，先修驱动器 |
| **S4** | 官方容器不可用且无替代靶 | L2a 失效 → 改判为纯静态 + 自研回放，并**显式下调**相关结论的证据等级 |
| **S5** | 台账出现无来源结论且无法补齐 | 该单元不算完成，不许进下一里程碑 |

**升级/降级**：任一单元成本远超预估（如需新的运行期插桩能力）⇒ **回到本节显式重估**，不硬撑。

### 6.1 防中断规范（来自本次会话的教训）

上一轮工作就是"在钉最后几个问题时上下文耗尽、结论悬空"，因此：

- 每个单元收尾必须留下**自包含接续块**：产物清单 + 原始输出 + **可重跑命令** + 未决项；
- 任何单元必须能"换会话、换人"接上，**不依赖对话记忆**；
- M0 的产物里包含这个接续块的**模板**。

## 7. 本设计明确不做的事（范围边界）

- **不写实现代码**，不做玩法移植或重写本身；
- **不深入另外 13 个服务进程的行为**（auction/guild/community/point/statics/dbmw×3/monitor/secsvr/relay/stun/bridge/coserver/manager）——它们只在"重写需要的进程拆分"要求时，做到**存在、不崩、契约与目录一致**；
- **不纳入官方独有系统**（D2，进待评估队列）；
- **不做游戏内键鼠自动化**（D3：批次由人操作，脚本只负责前置/启动/采集/收尾）；
- **不重做已闭合的登录→频道链**（`SPEC-login-to-channel.md` 的结论继续有效，只在本工程要求时被引用）。

## 8. 沿用的证据纪律（本项目既有约定）

- **六类标记**：`[静态]` `[抓包]` `[真机]` `[回放]` `[推断]` `[未验证]`，外加 `[作废]`（被推翻时加，并指向推翻它的证据）。定义见 `.recon/onboarding.md` §4。
- **矛盾留痕**：推翻旧结论不删原文，标 `[作废]` 并指向新证据。
- **探针纪律**：命名可识别、有生命周期、观测完退役、**不进入生产路径**；价值写进结论而非留在代码里。
- **可重跑命令**：任何写进知识层的结论都必须附一条能复现它的命令。
- **一次只改一个变量；先写预期再跑；先写"如果失败会看到什么"**。
