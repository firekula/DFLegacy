# GM 多物品发信与 v0.1.9 发布设计

依据用户本轮明确要求实施：先检查其他副本，再优化后台附件格，保持金币行为，完成报告、文档、提交推送与 Docker／客户端发布；线上容器由用户次日更新。

## 约束与方案

- ACT1 原客户端 NOTI 97 每封邮件只有一个物品，Mail 对象只有一个物品指针；不能只增加协议附件数组。证据：已核对原版 DNF.exe SHA256 6b4850beaf67ec61adb04ae17f119f16278dd05e97b8ffca871a9bdb547de0d5，分发表 0x42A081 的第 97 项指向 0x4281F9；读取及构造单物品分别在 0x4282FF..0x428390，Mail 构造函数 0x80B9C0。
- 采用 GM 多格输入、自动拆成多封原生邮件。改变客户端收件协议需要完整重做原生 UI，不适合作为本次后台优化。
- 实现者选择后台单次最多 10 个物品格，明确这属于管理操作上限，不是原版邮件附件上限。空列表只发一封文字／金币邮件。每格独立 ID、数量，沿用物品类别和时装能力选项。
- 金币只附第一封，正文及发件人保持一致；不追加可能超出编码长度上限的正文后缀。
- 指定角色和全体角色发送都支持。对每个角色先校验全部物品、邮箱总容量，再原子提交全部邮件。全体发送仍按角色报告成功／失败，失败重试不重复成功角色的任何附件。
- 保留旧单附件请求与旧存档格式。新可选 Attachments 为 null 时不写入 JSON，以保持旧群发指纹。新列表与旧附件字段同时使用应拒绝歧义输入。
- 每角色收件箱最多 255 封的现有限制继续生效。新增 MailIds 响应，同时保留 MailId 为第一封，旧记录可仅含 MailId。
- 客户端启动优化发布保持 v0.1.8 固定原生入口字节，避免现有安装的入口稳定性校验拒绝新版本。新的托管程序缺少 validated 记录时必须一次完整验证并迁移记录，后续走记录快径；原生 startup.dat 的新入口实验本轮不作为自动升级入口。
- 正式发布目标 v0.1.9：Gitea 完整源码、GitHub 净化源码快照、GHCR 服务端和 GitHub x86/x64 普通／测试客户端更新。不启动或更新线上容器，不修改 PVF。

## 验收

多格 UI 增删及恢复群发预览；单个／十个／超限／无效附件；金币只发一次；旧字段兼容；邮箱剩余容量不足完全拒绝；持久化故障与重复操作不重复奖励；旧已预览群发仍可发送；在线通知与原生逐封领取。客户端 v0.1.8 到新版迁移、记录缺失／损坏、旧入口保留及四路清单校验。公开产物不包含私有符号、账号或存档。
