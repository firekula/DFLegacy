## 1. 决策与目标（2026-10-02 用户裁决）

用户裁决原文：**"整个多人副本的部分，都按照官方版本逆向逻辑证据重写"**；范围选择为**六块全选**（含跨端 UDP 中继）；执行策略选择为**全量清单 + 分片替换**（旧实现按片作废）。

由此确定三个判断：

1. **语义权威 = 官服 `df_game_r`**（符号完整：352,694 条符号、402 个派发器、1248 个 `put_header` 调用点、命令表 CMD 608 / NOTI 563 项）。见 `.superpowers/sdd/2026-09-29-dungeon-party/work/official/`。
2. **可达权威 = 本客户端 `DNF.exe` 1.0.1.9**（通知跳转表 `0x42A081`，152 个 case，case N = `NOTI N`，default = `0x42A069`）。
3. **"对齐"不是一次性动作，而是可复核的结论集合**：每一条协议行为都要能指到官服地址与客户端处理器；指不到的，进清单并显式标 `[未验证]`。

目标态：多人副本的**每一个包、每一次状态转移、每一个定时器**都有官服证据；没有证据的行为不许留在生产路径上（要么删，要么标 `[未验证]` 并隔离在显式开关后）。

## 3. 两层证据与裁决规则

### 3.1 两层各管什么

- **语义层（官服 `df_game_r`）**决定"**应该做什么**"：命令号、包布局、字段语义、状态机转移、定时器。
- **可达层（本客户端）**决定"**做了有没有用**"：该通知的 case 是否存在、处理器读哪几个字段、读到之后改哪个状态。
- 单纯"官服有"不足以落地；单纯"客户端能跑"不足以称为对齐。**两条都要，冲突处进裁决表。**

### 3.2 四条裁决（清单里每条必须有且只有一条）

| 裁决 | 含义 | 落地要求 |
| --- | --- | --- |
| `对齐` | 官服与客户端两层都成立 | 按官服实现；单测钉字段与状态转移；真机观察点写进清单 |
| `保留` | 客户端可达层不成立或与官服冲突，但为了本客户端可用性保留 | 必须写：理由、用户可见后果、官服原语义、可移除的时间点 |
| `无法实现` | 官服机制在本客户端无落点（处理器不存在或落到 default） | 记录用户可见后果；不写"试错补包"；必要时按官服照发并标注"本客户端无反应" |
| `待真机` | 静态已定，客户端行为未观测 | 必须给出可判定的观察点（日志关键字 / 屏幕现象），排进真机里程碑 |

### 3.3 范例：`NOTI 86` 的裁决（本次会话新证，作为裁决表第一条）

- `[静态]` 官服 `DisPatcher_GetItem::process`@`0x081c35c0` 在 `0x081c3a42`–`0x081c3ac1` 构造 **class 0 / cmd `0x56`（=86）**、载荷 `u8 5` + `u16 拾取者 uid` + `u32 索引`，`finalize(1)` 后 `GameWorld::send_all` —— 即**拾取时向全场广播"地面物没了"**。
  > 复现：`.superpowers/sdd/2026-09-29-dungeon-party/work/` 下 `python dis_range.py 0x081c35c0+0x728 --show 0x081c3a20,0x081c3ad0`
- `[静态]` 本客户端 86 号处理器 `0x427104` 只实现子类型 **1 / 2**（文本广播），其余值 `jmp 0x42740F → jmp 0x42A069`（公共收尾 = **空操作**）；官服发的是 5。
  > 复现：`python -c "import dnf; print('\n'.join(dnf.dis(0x427104,30)))"`（`dnf.py` 在 `friends-protocol-recon/work/`）
- `[静态]` 客户端里删地面物只有两处调用点：`0x4224CB`（`NOTI 39` 内）与 `0x4229BD`（`NOTI 93` 内），两处都以**载荷 uid == 我的 uid**（全局 `0xb75a40`，经 `0x4052d0` → `registry->Find(uid)` 证实是 uid）为门；且 `NOTI 39` 在移除后**立刻把物品插入本地背包** ⇒ 不能借它清掉队友那件。
- **裁决**：`对齐` + 后果说明。服务端按官服发 `NOTI 86(5)`；**记录"本客户端画面不会消失"**（用户可见后果），`STATUS.md` §2.7 P4 的口径随之修订；**不**实现"照官服 7 字节另发一条移除包"这句写在 `GameProtocolEngine.cs:3682-3690` 注释里的旧结论（它是空操作）。

### 3.4 版本差规则

官服二进制（`df_game_r`，容器 `qf1031`）是**比 2008 客户端更晚的构建**。遇到"官服有、本客户端无"的机制：默认**按官服照发**并在清单标注客户端无反应；**不静默丢弃**，也不为它编造客户端行为。反之"客户端会发、官服不处理"的上行命令同样入清单（如 `CMD 142` 与官服 135/142 的语义差，见 `STATUS.md` §2.7 第 13 条）。

## 4. 目标架构

### 4.1 所有权表（每个行为只能有一个所有者）

| 所有者 | 拥有 | 允许依赖 |
| --- | --- | --- |
| `PartyRuntime` | `PartySlotTable`、host/manager 槽位、名册版本、loaded 标志、leave/give-up 状态 | `DungeonInstanceRegistry` 的读接口 |
| `PeerTransport` | 每成员 endpoint 表、nat/mtu、host 公告、中继/打洞状态 | `PartyRuntime`（槽位） |
| `DungeonEntry` | 选图状态、待入队信箱、入场序列、区域门禁 | `PartyRuntime`、`DungeonInstanceRegistry` |
| `RoomFlow` | 房间代数（room generation）、推进裁决、加载门槛、`NOTI 29`/`NOTI 30` 触发 | `DungeonInstance`（房间/怪物）、`PartyRuntime`（loaded） |
| `LootRouting` | 地面物生命周期、拾取仲裁、routing 状态机（候选/选择/超时/放弃/归属） | `DungeonInstance`（掉落账本）、`PartyRuntime`（槽位） |
| `Settlement` | 结算代数、卡表归属、选牌（手动/自动）、奖励发放、EPLP/回城定时器 | `LootRouting` 的读接口、`PartyRuntime` |
| `DungeonInstance`（模型层） | 房间/怪物/掉落**账本**与并发不变式 | 无（纯模型，不发包） |
| 会话层（`EntranceService`） | 读包 → 校验 → 交给模块 → 按收件人投递 | 全部模块的**门面**接口 |

规则：

1. **会话层不再独立决定任何副本语义**（谁是 host、能否换房、是否全员加载、能否结算、是否回城）。
2. **锁内只做状态判断/转移并产出"待发包描述"**；写流、跨会话投递、日志一律在锁外（沿用 `DungeonInstance.cs` 既有锁模型）。
3. **语义与字节分离**：`DFLegacy.Protocol/GameProtocolEngine.cs` 是唯一知道字节布局的地方；模块只产出意图记录。**每个构包函数的文档注释必须带**：官服地址（或"官服无此包"）+ 客户端可达性结论 + 裁决。
4. **禁止**：一个状态有两个真源；新增"补单个包试错"的路径；模块直接持有 `stream`；绕过清单直接改协议。

### 4.2 单人隔离（硬边界）

单人实例仍以角色 id 为键、`IsParty == false`、单成员；单人**立即**满足加载门槛、**不进入**队伍广播 / routing / 门口裁决 / 结算代数。所有组队专用新增逻辑以 `IsParty` 为门，并由"单人包序列逐字节回放"守住零回归（§8）。

### 5.2 客户端能力表（可枚举，不是猜）

- **通知表**：`0x42A081` 跳转表 + `friends-protocol-recon/work/jt.txt`（已有）；default 名单：`25,52,62,63,67,108-119,129,133,135,146,147`。

### 5.3 切片计划 `slices.md`

每片一张卡：片号 / 范围 / **该片删除的旧实现（文件:行）** / 依赖 / 自动化用例 / 真机验收点 / 完成定义（DoD）。

### 5.4 工具固化

把本次会话这类"查跳转表 / 查处理器 / 查调用点 / 查全局"的脚本收成可复用工具（`work/` 下脚本 + `.recon` 工具条目），并写清命令行与产物；**不要**每次会话重写一遍。

### 5.5 计划的分层（避免"在证据之前写实现细节"）

- **第一层（本次要产出的实施计划）**：Phase 0 的四件产出物 + 每片的**范围/依赖/DoD/删除清单**。粒度到切片，不到函数。
- **第二层（每片开工时产出）**：该片的 `S<n>-brief.md` —— 具体到"改哪个函数、加哪个测试、删哪几行"，**前提是该片相关清单条目已 8 字段齐备**。
- 理由：在官服证据闭合前写函数级实现细节，等于把猜测写进计划；这与 §11"不在证据闭合前实现未证实规则"是同一条纪律。

## 6. 分片执行与验收

### 6.1 每片的流水线（不可跳步）

1. 清单条目（含 8 字段）就位；
2. TDD：先写红测试（模型层 + 构包层可测的部分）；
3. 实现（模块内）；
4. **删除该片旧实现**（DoD 的一部分：旧代码行数必须消失，不能只被绕过）；
5. 定向 smoke 全绿 + 变异验证（改坏实现必须变红）；
6. 独立评审（不同视角的评审者，按项目既有做法留评审结论文件）；
7. 真机里程碑（双客户端，时间**先与用户确认**）；
8. 中文提交 + 台账更新（`.superpowers/sdd/2026-10-02-party-dungeon-official-rewrite/progress.md`，只增不删）。

### 6.2 过渡期完整性（新规则）

每片合并后，产品必须仍能端到端运行（单人完整流程 + 组队到"该片已完成"的能力边界）。**任何临时缺失的能力必须写进该片 DoD 的"已知缺口"**，不许静默回归；也不许用"补一个包让它先能跑"的方式掩盖缺口。

### 6.3 与真机时间的关系

真机里程碑需要用户操作两个客户端（`G:/Game/DNF_ACT1/DF/town-test`，账号 `test`/`test`、`shizuku`/`shiruku`）。切片 DoD 里写明"本片需要几次真机、看什么"；**开工前先约时间**，不临时占用。

## 7. 验收矩阵

### 7.1 自动化

- 每片定向 smoke 全绿（现基线：`--party-card` / `--store-write-transaction` / `--dungeon-reward-commit` 各 0 failures，服务端构建 0 警告 0 错误，实测于 `db46e38`）；
- 变异验证：每条新护栏改坏实现必须变红（实测后回滚，记录在台账）；
- **单人逐字节回放**：单人包序列与改造前日志逐条比对（`CMD 74` 两个重载已有逐字节断言）。

### 7.2 真机

- 按清单的"验收判据"列汇总成一份真机脚本（每步：怎么操作 / 看屏幕什么 / grep 哪个日志关键字）；

- 单人完整流程一次（零回归）。

### 7.3 旧 P 表作废说明

`STATUS.md` §2.7 的 P1–P8 结论属于**旧实现**。分片重写会逐片作废它们（P1/P3/P5 与「组队翻牌验收」小节涉及的代码被 S4/S6 触碰时即失效），**重写完成后按 §7.2 重跑并重填**，中间态不作为验收依据。

- **查表前置**：任何官方通知/命令落地前，先查通知跳转表与上行命令表；不可达的必须进裁决表（§3.2），不许"先发了试"；
- **不许补包试错**：单个补包解决症状的路径一律拒绝，除非清单里有对应官服证据；
- **不许静默丢官服机制**：官服有、客户端无反应的，照发并标注；
- **不许两个真源**：同一状态出现第二个所有者即视为设计缺陷，评审必须打回。
