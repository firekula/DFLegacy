# 游戏面帧结构 —— 钉证据结果（2026-10-05 晚）

> **⭐ 头号结论（本文其余部分都是在它之前得出的，保留以留痕）**：
> **游戏面帧头是 13 字节，不是 10 字节。** 字段布局由官方 cfg 逐字给出，
> 并由"C→S 序号完美递增"独立证实。见 §0。

## §0 【最终】帧头 = 13 字节（官方字段名 + 双向验证）

**判据一（官方 cfg 白纸黑字）**：`/home/neople/game/cfg/siroco11.cfg` L82–89

```
82: header_classification = 0 1      83: header_msg_no        = 5 1
84: header_sLength        = 1 4      85: //header_garvage     = 6 1
86: header_checksum       = 7 4      87: header_sequence      = 11 2
88: header_load_interval  = 10       89: header_mangled_length = 13
```

字段与宽度：`classification(1)+msg_no(1)+garvage(1)+sLength(4)+checksum(4)+sequence(2) = 13`

**判据二（独立、实测）**：C→S 方向的 `[11..12]` 是 **uint16 LE 递增序号** ——
四条 C→S 流实测 **20/20、20/20、20/20、5/5** 逐帧 +1 起于 0。
**载荷不可能是完美计数器** ⇒ 这两个字节必是头字段 ⇒ 头至少 13 字节。
（`work/nail-header13.py`、`work/nail-header13-verify.py`）

**客户端方向的实际布局**（观测）：

| 偏移 | 宽 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `classification` | `0x01`=CMD / `0x00`=NOTI |
| 1 | 1 | `msg_no` | opcode |
| 2 | 1 | `garvage` | **官方字段名就是 garvage**（拼写如此）；实测 `{0,1,2}` |
| 3..6 | 4 | `sLength` | uint32 LE，**含整帧** |
| 7..10 | 4 | `checksum` | 算法**未解**（见下） |
| 11..12 | 2 | `sequence` | uint16 LE，C→S 递增 |

**旧作的修正**：
* `[作废]` "10 字节头"。**切帧仍然正确**（切帧只看 `[3..6]` 的 size，与头长无关 ——
  实测两个模型在全部 12 条流上都恰好铺满），所以那个错误**没有污染切帧类结论**
  （B0 的"恰好铺满"、Task 11 的重放比对都仍成立）。它污染的只是**载荷起点**：
  载荷从 **13** 起，不是 10。
* `[作废]` "`[7..9]` 是 3 字节独立字段 / 疑似校验和"。它其实是 **4 字节 `checksum` 的前 3 字节**。
* `[作废]` "`[2]` 恒 0"。官方名叫 `garvage`，实测 `{0,1,2}`。
* **之前观测到的 `hdr[7] == payload[1]` 180/180，在 13 字节视图下是
  `checksum[0] == sequence[0]`（S→C）** —— 这条关系**仍未解释**，但因为头布局已定，
  它的意义变了：不再是"头字节是载荷字节的副本"，而是**两个头字段首字节相同**。
  留作待查（见下）。

**仍未解**：`checksum` 的算法。试过 `adler32`/`crc32`/`sum32`（对载荷、对整帧）
在 90 帧上**全 0 命中**。**不阻塞**：原样重放整帧可通过。

## §1 修正：`[7..9]` **不是**校验和（我先前过度解读了）

**旧结论**（`work/out/B0-batch-report.md` §4、`work/driver/dnfdrive.py`）：
`[7..9]` 语义未定，疑似校验/序号 → `[未验证]`。
后来我在 game 服日志里读到

```
[14:37:14] bool CUser::Parsing(int)(1850): [CHECK SUM] check_sum error PACKET : ENUM_CMDPACKET_LOGIN
```

时间戳正对应我那次"重放 B0 旧帧"，于是**我把 `[7..9]` 定性为校验和**。

**这个定性是错的**（或者说至少是不完整的）：日志只说明"某个包级别的校验没过"，
**没有**说那个校验位于 `[7..9]`。我拿一个现象的名字去给一个字段命名，属于
"把一个观察推广成一条规则"，违反证据纪律。

**现在的实测**：`[7..9]` 无法用任何标准校验和解释（§2），而它与载荷的关系是
"抄字节"而不是"算校验"（§3）。

## §2 标准校验和全部被否证

对 S→C 两条抓包各 90 帧，试了 16 个候选算法（`sum8/sum16/xor8/adler32` 各字节、
`crc32` 各字节，覆盖 `payload[2:]` 与整载荷），看哪个能复现 `payload[1]`：

| 抓包 | 最好成绩 | 命中率 |
|---|---|---|
| `streams-live/10013-2343.bin` | `adler32(body)>>24` / `sum8(body)` 等各 1/90 | **1.1%** |
| `streams-vm/10013-13681.bin` | `adler32(body)&0xff` / `crc32(body)>>24` 各 2/90 | **2.2%** |

随机基线 ≈ 1/256 = 0.39%，16 个候选中出现 1–2 次命中**正是纯偶然的水平**。
⇒ **没有一个是它。** 项目符号表里的 `Encryption::Adler32` 也不是。

## §3 `hdr[7] == payload[1]`：100% 成立，且有方向性

对**每一帧**统计（`nail-frame-structure.py`）：

| 流 | 方向 | `hdr[7]==payload[1]` | 帧数 |
|---|---|---|---|
| `streams-live/10013-2343.bin` | S→C | **90/90** | 本次活账号登录 |
| `streams-vm/10013-13681.bin` | S→C | **90/90** | B0 抓包 |
| `streams-live/2343-10013.bin` | C→S | 0/21 | |
| `streams-vm/13681-10013.bin` | C→S | 0/21 | |

**180/180 成立**（两条独立抓包），C→S 方向 0/42 **完全不成立**。
⇒ `hdr[7]` 是 `payload[1]` 的**副本**，不是算出来的校验。

其他候选关系全部不成立：`hdr[7]==payload[0]`(1/210)、`hdr[8]==payload[2]`(0/210)、
`hdr[9]==payload[3]`(0/210)、`hdr[7:10]` 出现在载荷任意位置(0/210)、
`hdr[7]^payload[0]` 恒定(70+ 种取值，无)…

## §4 最关键：载荷**基本是确定性的**（不是会话加密）

**方法上的坑（留痕）**：第一版按 `(cat,id,size)` 分组，但同一类型在一条流里可能
出现多次且内容不同（`NOTI183(31)` 出现两次），混组后把所有帧都误判成"随机"。
修正为按 **帧类型 + 出现序号** 跨会话配对后：

| 逻辑同帧 | 载荷 | 恒定 | 变化偏移 |
|---|---|---|---|
| `NOTI1(450)` 第0次 | 440 B | **429/440 (97.5%)** | `[0,1,2,3,4, 352,353,354,355, 359,360]` |
| `NOTI183(31)` 第0次 | 21 B | **18/21 (85.7%)** | `[2,3,4]` |
| `NOTI183(31)` 第1次 | 21 B | **18/21 (85.7%)** | `[2,3,4]` |

样本来自**三个不同会话**：所有者登录的抓包、我成功重放的回复、我被踢那次的回复。

**⇒ 游戏面载荷是"确定性二进制结构 + 开头 3–5 字节会话相关前缀"。**

这条**推翻了我在 Task 11 报告里的说法**："活账号与 B0 两份首帧同样 403 B、却有 399
字节不同 ⇒ 载荷按会话随机化、不可 patch"。
**那个对比拿的是两个不同账号（uid=2 vs 18000008）的登录帧** —— 账号不同，令牌自然不同。
把"账号差异"读成了"会话随机"，是**变量没控住**。已 `[作废]`。

## §5 登录帧里没有可恢复的 RSA 令牌

拿**两把**公钥分别扫 C→S 首帧（413 B，载荷 403 B，共 148 个 256 B 滑窗）：

| 公钥 | 模数 | 命中 |
|---|---|---|
| VM 游戏服 `publickey.pem` | `BEF69F43…` | **0** |
| 登录服 PHP `rsa.php` 推出的公钥 | `E21F97…` | **0** |

⇒ 令牌（若在帧里）被变换过，或根本不经由该帧。**"原样重放"仍是唯一可行路径**。

## §6 `[2]` 不是恒 0（又一条被样本不足害了的结论）

**旧结论**（`dnfdrive.py` / `B0-batch-report.md`）：`[2] 恒 0（语义 [未验证]）`。

**实测**（`work/nail-byte2.py`，8 条流共 235 帧）：

```
C→S 2343-10013.bin (firekula, 21 帧)  {0:12, 1:6, 2:3}
C→S 13681-10013.bin (uid=2,    21 帧)  {0:12, 1:6, 2:3}     ← 与上一行**完全相同**
S→C 10013-2343.bin                (90 帧)  {0:30, 1:39, 2:21}
S→C 10013-13681.bin               (90 帧)  {0:30, 1:39, 2:21} ← 与上一行**完全相同**
S→C 30011-46386.bin (docker 拒绝,  5 帧)  {0:5}
```

**两条独立结论**：
1. `[2]` 取值是 `{0,1,2}`，**不是恒 0** ⇒ 旧结论是**样本不足导致的错误推广**。
2. 两份**不同账号**的抓包，`[2]` 的取值分布**逐个相同** ⇒ `[2]` 是**按帧类型确定的**
   字段值，**既不随会话、也不随账号变化**（同一 `(cat,id)` 下基本恒定；
   唯一例外 `S→C NOTI48` 出现 `[0,1]` 两种，待查）。

## §7 补齐：同账号两次登录的 C→S 帧 —— **登录帧是确定性的**

**这是本轮唯一需要人配合的实验**（抓包脚本 `work/capture-login.sh`，过滤 `10013 + 7001`）。

| 对比 | 结果 |
|---|---|
| **同账号**（firekula）两次登录的 C→S 首帧 | **402/403 字节相同**，只有 `payload[0]` 一个字节不同 |
| **不同账号**（firekula vs B0 的 uid=2） | 4/403 相同（随机基线期望 ≈ 1.6）⇒ **完全不同的数据** |
| 同账号的其它帧（CMD2/CMD4/CMD8/CMD37/CMD66/CMD70/CMD82…） | 全部**只差 1 字节** |

⇒ **登录帧 = "按账号确定的数据 + 1 个会话字节"**。这正是"对 uid 的确定性签名"的特征
（同一个 uid ⇒ 同一个签名；不同 uid ⇒ 完全不同的 256 字节）。

**但令牌仍未定位**（`work/nail-token-hunt.py`）：用登录 PHP 私钥**自己算出**
uid=18000008 的正确签名，然后

| 试的变换 | 结果 |
|---|---|
| 签名原样出现 / 取反后出现 | 否 |
| 逐偏移 `W XOR 签名` 是否为常数 | 148 个偏移**全部否**（最小取值种类 149/256 = 高熵） |
| 逐偏移 `W ± 签名` 是否为常数 | 否 |
| 搜 `32×0x01`、10 B 尾巴 `55 91 45 10 01 04 03 03 01 01` | 均**未出现** |
| 搜 uid 大端/小端 4 字节 | 均**未出现** |

⇒ 帧里的令牌**不是**登录 PHP 那把钥匙签的明文，也不是"异或/加减常数"级别的弱变换。
**这是 M1 单元②要解决的问题**（本轮把它从"未知"钉成了"已知不是这些"）。

## §8 补齐：实际运行的 binary 与 M0 分析的那份差 103 字节

| | |

按**节表**分类（`work/nail-patch-sections.py`，脚本 `work/nail-patch-sections.py`）：

.dynstr   .rodata/字符串    1 段

落在 **M0 派发器家族区间内**的有 **5 处**（`work/nail-patch-impact.py`）：

| 文件偏移 | VA | 家族 |
|---|---|---|

| `0x001a57cd` | `0x081a57cd` | **`EnterPVP`** |

**⇒ 可执行的结论**：M0 的 425 家族目录 / 1171 条 opcode 映射 / 7273 条 handler 对 VM
**直接适用**，**除了这 3 个家族**（`SelectDungeon`、`EnterPVP`、`ModItemAttr`）——
引用它们的地址级结论时必须逐个复核。这三处也正是"私服改过的玩法逻辑"
（选副本、进 PvP、改物品属性），重写时**属于非官方部分，不要照抄**。

判据留痕：上一版 `nail-patch-impact.py` 用 PT_LOAD 分类，得出"47/47 落代码段" ——
**那个分类太粗**（该 RX 段同时含 `.text`/`.rodata`/`.dynstr`），已用节表重做并修正为 46/47。

§4 的结论建立在**同一账号三次登录**上，但那三次里 C→S 方向**只有一份**（`2343-10013.bin`）。
所以"**C→S 登录帧是否也确定性**"**还没有直接证据** —— 而这个恰好是决定
"M1 单元②能不能离线构造登录帧"的那一条。

**需要的实验**：抓**同一个账号（firekula）两次登录**的 C→S 首帧，逐字节 diff。
* 若两份**几乎相同**（只差少数几字节）⇒ 登录帧可离线构造，M1 单元② 大幅简化；
* 若两份**完全不同** ⇒ 登录帧含会话随机量，必须走完整登录链。

抓包方法：`work/capture-login.sh start` → 让所有者登录一次 → `stop` → `vmget.py` 取回。
