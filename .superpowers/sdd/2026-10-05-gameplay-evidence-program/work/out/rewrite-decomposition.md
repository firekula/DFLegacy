### 1.2 依赖方向（从各 cfg 的对端字段读出）

```
客户端 ──HTTP──> httpd:1234 (logincon.php)  ──发令牌──> 客户端
客户端 ──TCP───> df_channel_r:7001 ──> df_bridge_r:7000 ──> df_game_r(每频道)
df_game_r ──UDP──> monitor:30303 / statics:30503 / guild:30403 / doublecheck:30703
df_game_r ──TCP──> auction:30803 / cera_auction(point):30603 / relay:7200
df_game_r ──UDP──> stun:2311-2313（NAT 探测）+ hades:31003
df_game_r ──内部──> 127.0.0.1:20013（exchange server，同进程另开）
df_game_r ──MySQL──> 3306（taiwan_cain_2nd 等）
guild / monitor / statics ──TCP──> df_dbmw_r:20203/20403/20303
monitor ──> manager:40403
auction / point ──MySQL 直连──> 3306（各自的库）
```

**关键观察**：`df_game_r` 是**依赖扇出最多的节点**（对 9 个外部服务有依赖），
而 `df_channel_r` / `df_bridge_r` 是**客户端唯一入口**。

## 二、重写切分：建议 7 个部分

排序原则：**依赖在前** + **证据最全的先做** + **正在流血的最先**（spec §5.1）。

### 第 0 部分 · 契约层（所有进程共用的地基）

**内容**：两套帧模型、密码层（AES/zlib/会话密钥）、令牌、`.cfg` 配置格式、
日志目录与文件名（`LogYYYYMMDD.{log,error,cri,init,debug,snap,money,history}`）、
`pid/*.pid`、启动方式（`./<exe> <server> start &`）、DB 连接与分库约定。

**证据现状**：**最全**。帧层/密码层/令牌都有实证（Task 9/10/11 + 本轮钉定），
配置与目录结构已逐文件读过。

**为什么排第一**：后面每一部分都要用它。做错这里，全部返工。

### 第 1 部分 · 登录/账号面（替代 Apache+PHP 那一层）

**内容**：`logincon.php` 的完整协议（RC4+hex 包装、`$msgkey='Passwordisaw'`、
`Temp_Key` 握手、`login|user|md5(pw)|mac` 请求格式）、账号表读写、
注册/改密/找回/充值等分支、令牌签发（46 B + 裸 PKCS#1 type-1）、服务器列表 XML。

**证据现状**：**好**。`logincon.php` 全文 393 行已下载并逐行读过
（`work/vm-files/logincon.php.txt`）；令牌构造被服务端源码逐字确认；
令牌格式已被 Task 10 独立实证。

**缺口**：`str_encode`/`str_decode`/`rc4` 的实现细节（需读 `rsa.php` 之外的包含文件）；
`Temp_Key` 的生成与存活期。

### 第 2 部分 · 频道/网关面（`df_channel_r` + `df_bridge_r`）

**内容**：7001 的 11 字节头协议、会话建立（`id=12` 会话密钥）、
频道表下发（`id=3`/`id=10` 的 `zlib(AES(...))`）、服务器/频道选择、
`bridge` 与 `channel` 之间的协议。

**证据现状**：**好**。7001 的帧层与密码层已实证（Task 9 的硬门 PASS），
且上一轮 `SPEC-login-to-channel.md` 已把登录→频道链闭合；本轮又抓到一份
**活的** 7001 流（`work/captures/streams-live2/14789-7001.bin` ↔ `7001-14789.bin`）。

**缺口**：`bridge ↔ channel` 的内部协议**没有取证**。
（两侧 cfg 都写 `7000`：`channel.cfg` 的 `bridge_ip/bridge_port = 127.0.0.1/7000`、
`bridge.cfg` 的 `this_ip/this_tcp_port = 127.0.0.1/7000` ⇒ 它们共用 7000，
抓包时**要按对端区分**，不能只按端口。）
**⟂ 修正留痕**：本文初稿把这条写成"7020 那条" —— 那个端口号是我**凭印象写的**，
cfg 里没有。已按实测改正。

### 第 3 部分 · 游戏服 `df_game_r`（**最大的一块**，按里程碑再切 10 段）

**内容**：spec §5.2 的 M1–M10，逐段对应**功能面**（不是派发器）。
**范围声明的来源**：M0 的 `work/out/opcode-map.tsv`（1171 条，`unknown=0`）。

| 段 | 功能面 | 备注 |
|---|---|---|
| 3a | 会话面（登录/选角/进频道） | M1；**已有成功+拒绝两条已知答案** |
| 3b | 城镇面（位置同步/同屏/聊天/打洞） | M2 |
| 3c | 单人副本 | M3 |
| 3d | 角色成长（物品/装备/技能/任务） | M4 |
| 3e | 经济与其它（商城/邮件/宠物） | M5 |
| 3f | 社交（好友/黑名单/在线状态） | M6 |
| 3g | 交易 | M7（V8–V12 是现成验收清单） |
| 3h | 组队 | M8 |
| 3i | 组队进副本 | M9 |
| 3j | 决斗/PvP | M10 |

**证据现状**：**分母全、行为面基本空**。425 家族 / 1171 条映射 / 7273 条 handler 齐备，
但**行为规格一份都还没有**（那正是 M1–M10 要产出的六件套）。

**⚠️ 特别注意（本轮钉出来的）**：这个 binary 被私服改过 103 字节，
其中 5 处落在 3 个家族里 —— `SelectDungeon`、`EnterPVP`、`ModItemAttr`。
**引用这 3 个家族的地址级结论必须逐个复核**，而且它们**属于非官方部分，不要照抄**。

**每段切分的粒度准则**（spec §3.1）：单元内命令数 ~10–40；跨单元的命令要互相显式引用。

### 第 4 部分 · DB 中间件（`df_dbmw_r` ×3）

**内容**：三个实例分别服务主库/统计库/公会库；与 `game`/`guild`/`monitor`/`statics`
之间的协议；分库契约（哪个进程写哪张表）。

**证据现状**：**只到配置层**。三个 cfg 已读全（`master_db_ip/port/acc/pwd/name`），
但**协议本身一条都没取证** —— 这是本评估里**最大的证据空白**。

**注意**：`dbmw` 是**游戏服业务读写的主要通道**，M3/M4 一碰持久化就会需要它。

**⟂ 修正留痕（我先前写错过一次）**：本文初稿写"`game` 不直连数据库，所有持久化都经 `dbmw`"，
依据是 `db_info_tw.cfg` 里只有服务地址、没有凭据。**那个依据不足** ——
`df_game_r` 的**每频道 cfg**（`siroco11.cfg` L68–73）里其实是**有** DB 凭据的：

```
db_thread_count = 3
master_db_ip    = 127.0.0.1
master_db_port  = 3306
master_db_acc   = game
master_db_pwd   = 20e35501e56fcedbe8b10c1f8bc3595be8b10c1f8bc3595b
master_db_name  = d_taiwan
```

（另外 `db_tbl_file = db_info_tw` ⇒ `db_info_tw.cfg` 是**表名清单/表定义**，不是连接信息。）
⇒ **正确说法**：`game` **有**直连 MySQL 的能力（`db_thread_count = 3` 说明它自己开连接池），
`dbmw` 是**另一条**通道（`guild`/`monitor`/`statics` 走它）。
**两者都要重写，但优先级待定** —— 需要先搞清楚"哪些表由 game 直写、哪些经 dbmw"，
这是第 4 部分开工前必须先取证的一条。

**教训**：我只看了一个 cfg 文件就下了全局结论（"game 没有 DB 凭据"）。
一个样本不足以支撑"没有"这类全称判断。

### 第 5 部分 · 辅助进程（`monitor` / `manager` / `relay` / `stun` / `coserver` / `statics` / `community`）

**内容**：按 spec §7 的原话，这一档只需要"**存在、不崩、契约与目录一致**"。

**证据现状**：配置层齐（端口/对端都读到了）；协议层**基本为空**。

**判断**：如果坚持 §7 的原始边界，这一档可以**最后做、且只做"能被 ping 通、不崩"**。
但**所有者已把范围扩大**（待评估队列全部纳入）⇒ 其中
`guild`/`auction`/`point`/`community` 相关的**功能面**已升级为必须重推导，
它们不再是"存在即可"。

### 第 6 部分 · 反外挂（`gunnersvr` / `secagent` / `zergsvr`）

**内容**：HackShield 系。二进制在 `/home/neople/secsvr/`，有 `HSPub.key`。

**证据现状**：**几乎为零**（进程在跑、有日志，仅此）。

**建议**：**明确排除**在本轮重推导之外 —— 理由：① 它与官服客户端的 HackShield
模块强耦合，而我们**不改客户端**；② 它的行为不影响玩法证据链；
③ 成本高、收益低。**需要在评审门显式确认这条排除**（因为"范围不缩"的裁决
可能被理解成包含它）。
