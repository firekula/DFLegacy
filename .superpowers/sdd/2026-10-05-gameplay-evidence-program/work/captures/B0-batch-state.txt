## 3. 两处**计划前提不成立**（实测偏离，收尾要还原的是"实际状态"而不是计划里的写法）

* **偏离 A：`netsh interface portproxy` 用不了 —— 需要管理员权限。**
  实测：`netsh interface portproxy add v4tov4 listenport=30011 ... ` →
  `The requested operation requires elevation (Run as administrator).`（exit 1）
  （`iphlpsvc` 服务是 Running，失败原因是权限而非服务。）
  ⇒ 改用**用户态 TCP 中继**：`work/batch-b0-relay.py`，监听 `127.0.0.1:30011` → 转发 `127.0.0.1:30021`。
  对客户端与容器的可观测行为与 portproxy 等价（容器侧看到的都是宿主 docker 代理发起的连接）。
  实测可用：`Test-NetConnection 127.0.0.1:30011` = True；中继日志记到 `conn#1 closed c->s=0B s->c=432B`
  （探针没发数据、容器回了 432 字节 ⇒ 端到端通）。
  **撤销 = 杀掉该后台作业**（不需要 netsh）。
  若所有者希望用内核级 portproxy：管理员 shell 跑
  `netsh interface portproxy add v4tov4 listenport=30011 listenaddress=127.0.0.1 connectport=30021 connectaddress=127.0.0.1`

* **偏离 B：抓包 sidecar 不是 `dfl-recon`，而是独立的 `dfl-sniff`。**
  计划 Step 6 说要 `docker rm -f dfl-recon` 再重建来抓包；但既有文档（`topology.md:400`、
  `dual-evidence.md:57`）显示上一轮抓包用的是另一个容器 `dfl-sniff`，且 `dfl-recon` 在 bridge 网络、
  **不在 dnf 的 netns 里**。重建 `dfl-recon` 只会毁掉 `c++filt`（本轮抓包用不到它，但后续可能要用）
  ⇒ **不动 `dfl-recon`**，按上一轮验证过的配方另起 `dfl-sniff`。

* **顺序（坑 9）**：`--network container:X` 的 sidecar 熬不过 `docker restart X` ⇒ 必须先重启 `dnf`、
  再建 sidecar。本次顺序正确，且建后自检 `ip -o addr show` **有 `eth0` 172.17.0.2/16** ⇒ netns 有效。

## 4. 抓包配置（当前正在跑）

```
docker exec dfl-sniff pidof tcpdump        # 本次 = 554
tcpdump -i any -s 0 -U -w /w/.superpowers/sdd/2026-10-05-gameplay-evidence-program/work/captures/e2e-official-to-game.pcap \
        "tcp port 7001 or tcp port 30011 or udp port 2311 or udp port 31011"
```
* 过滤器**没有**用 `greater N`（`open-questions.md:601`：它按链路层长度算，会把 62 字节的小载荷帧整批滤掉）。
* 链路类型 `LINUX_SLL2`（`-i any` 的必然结果），与上一轮 `pcap-streams.py` 处理过的一致。
* 活性已验证：一次 30011 连接即可让 pcap 从 24 → 1264 字节。
* 停止：sidecar 里**没有 `pkill`**（`open-questions.md:604`）⇒ 用 `kill $(pidof tcpdump)` 或 `docker rm -f dfl-sniff`。
